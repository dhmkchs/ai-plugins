# 인증/인가 흐름

## 인증 방식 비교

| 방식 | 저장 | 장점 | 단점 |
|---|---|---|---|
| 세션 쿠키 | 서버(세션스토어) + 쿠키 sid | 서버가 즉시 무효화 가능, 단순 | 상태 보관 필요, 수평 확장 시 공유 스토어 |
| JWT | 클라(토큰 자체에 클레임) | 무상태, 검증에 DB 불필요 | 발급 후 무효화 어려움(만료 전까지 유효) |

**JWT 무효화 문제**: 로그아웃·권한 변경을 즉시 반영 못 한다. 완화책:
- access 토큰 수명 짧게(5~15분) + refresh 토큰으로 갱신
- 블랙리스트(무효화 목록)를 서버에 두면 사실상 상태 보관 — JWT 무상태 이점이 줄어듦
- 민감 작업(결제·비번변경)은 재인증 요구

## 토큰 저장 위치 (프론트)

| 위치 | XSS | CSRF | 비고 |
|---|---|---|---|
| `localStorage` | ❌ 취약(JS로 탈취) | ✅ 안전 | XSS 하나면 토큰 유출 |
| httpOnly 쿠키 | ✅ JS 접근 불가 | ❌ 취약 | CSRF 토큰/SameSite 필요 |

권장: **access는 메모리, refresh는 httpOnly+SameSite=Strict 쿠키**. localStorage에 장기 토큰을 두지 않는다.

## 리프레시 흐름

```
1. 로그인 → access(단명) + refresh(장명, httpOnly 쿠키)
2. access 만료 → 401
3. 클라가 POST /auth/refresh (쿠키의 refresh 사용) → 새 access
4. refresh도 만료/무효 → 재로그인
```

- refresh 토큰 회전(rotation): 쓸 때마다 새 refresh 발급, 옛것 무효화 → 탈취 탐지
- 동시 401 다발 시 refresh 요청을 하나로 합친다(큐잉) — 중복 갱신 방지

## 인가 패턴

**인가는 리소스 접근 시점마다.** 미들웨어 인증 통과 ≠ 인가 완료.

### RBAC (역할 기반)
```
if (!user.roles.includes('admin')) return 403
```
단순하지만 "본인 것만" 같은 리소스 소유권은 표현 못 함.

### 리소스 소유권 (가장 흔한 누락)
```
GET /users/:id/orders
→ 토큰 사용자 id === :id 인가? 아니면 admin인가? 아니면 403.
```
이 검사가 없으면 **IDOR**: `/users/2/orders`로 URL만 바꿔 남의 데이터를 본다. 목록·상세·수정·삭제 전부에 적용한다.

### ABAC / 정책
속성(부서·시간·리소스 상태) 조합이 필요하면 정책 엔진으로 분리. 과하면 RBAC+소유권으로 충분.

## 체크리스트

- [ ] 모든 보호 엔드포인트가 인증을 강제하나 (기본 deny)
- [ ] 리소스 접근마다 소유권/역할을 서버에서 확인하나 (프론트 숨김에 의존 X)
- [ ] 401(미인증)과 403(권한없음)을 구분하나
- [ ] 토큰이 URL·로그·에러 응답에 안 남나
- [ ] 민감 작업에 재인증/레이트리밋이 있나
