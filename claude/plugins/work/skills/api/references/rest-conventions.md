# REST 규약 상세

## 메서드 · 멱등성 · 안전성

| 메서드 | 안전(safe) | 멱등(idempotent) | 용도 |
|---|---|---|---|
| GET | ✅ | ✅ | 조회. 부수효과 없어야 함 |
| POST | ❌ | ❌ | 생성·비멱등 액션 |
| PUT | ❌ | ✅ | 전체 교체(같은 요청 여러 번 = 같은 결과) |
| PATCH | ❌ | 보통 ❌ | 부분 수정 |
| DELETE | ❌ | ✅ | 삭제(두 번 삭제해도 최종 상태 같음 → 두 번째 404 대신 204도 허용) |

**멱등성이 중요한 이유**: 네트워크 재시도. 클라가 응답을 못 받고 재요청할 때, 멱등이면 안전하다.
비멱등 생성(POST)에 재시도 안전이 필요하면 **Idempotency-Key 헤더**로 중복 생성을 막는다.

## URL 설계

- 소문자·하이픈: `/user-profiles` (언더스코어·카멜케이스 X)
- 복수 컬렉션 + ID: `/orders/9`
- 계층은 3단계까지: `/users/1/orders/9`. 더 깊어지면 `/orders?userId=1`로 평탄화
- 필터·정렬·페이징은 쿼리스트링, 리소스 식별은 경로

## 상태코드 세부

- `201 Created` + `Location: /users/123` 헤더 (생성된 리소스 위치)
- `202 Accepted`: 비동기 처리 시작됨(아직 완료 아님) — 상태 조회 URL 제공
- `204 No Content`: 성공했지만 본문 없음 (DELETE, 일부 PUT)
- `304 Not Modified`: 조건부 요청(ETag/If-None-Match) 캐시 유효
- `409 Conflict`: 상태 모순(중복, 낙관적 락 버전 불일치)
- `422 Unprocessable`: 문법은 맞지만 의미 검증 실패 (400과 구분해 쓰는 팀도, 400으로 통일하는 팀도 있음 — 팀 규약 고정)

## 캐싱

- `GET`에 `ETag` / `Last-Modified` 부여 → 조건부 요청으로 대역폭 절약
- `Cache-Control`로 캐시 정책 명시 (`no-store`, `max-age`, `private`)
- 뮤테이션 후 관련 캐시 무효화 전략을 계약에 포함

## 응답 envelope — 쓸지 말지 정한다

두 스타일 중 하나로 통일:

```json
// A) 벌거벗은 리소스 (단순, HTTP 상태로 성패 판단)
{ "id": "1", "name": "..." }

// B) envelope (메타데이터 동반, 목록·에러와 형태 일관)
{ "data": { "id": "1" }, "meta": { ... } }
```

목록은 페이지 메타 때문에 envelope가 거의 필수. 단건까지 맞출지 팀에서 정한다. **섞지 않는다.**

## GraphQL이라면

- 오버페칭/언더페칭이 실제 문제일 때, 클라가 필드를 고르는 이점이 클 때 선택
- N+1은 DataLoader로 배칭, 깊이/복잡도 제한으로 악의적 쿼리 방어
- 에러는 HTTP 200 + `errors` 배열이 기본 — REST 상태코드 감각과 다름을 팀이 인지
- 스키마가 곧 계약·문서. 페이지네이션은 Relay cursor connection 규약 참고
