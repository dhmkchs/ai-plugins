# Feature Build

구현이 끝났는데 요구사항 하나가 빠져 있는 것, 동작하는데 리뷰가 통과되지 않는 것,
둘 다 원인은 같다. **무엇을 만들지 확정하지 않고 시작한 것.**

순서를 지킨다. 1~2단계에 전체 시간의 20%를 쓴다. 여기서 아낀 시간은 나중에 두 배로 나간다.

> Jira 티켓으로 관리되는 작업이면 `/work:plan` → `/work:start` 체인을 쓴다.
> 이 스킬은 티켓 없이 요구사항을 바로 구현할 때의 절차다. 원칙은 같다.

## 1. 요구사항 표로 분해

요구사항 문서·티켓의 문장을 하나씩 표로 옮긴다. 문장 하나가 행 하나다.

```
| # | 요구사항 (원문 인용) | 필수/선택 | 검증 방법 | 상태 |
|---|---|---|---|---|
| 1 | "중복 이메일은 거부한다" | 필수 | 테스트 `rejectsDuplicateEmail` | ☐ |
| 2 | "응답은 1초 이내" | 선택 | 부하 측정 | ☐ |
```

표를 만드는 과정에서 놓친 요구사항이 항상 1~2개 나온다. **그게 이 단계의 값이다.**
그리고 이 표가 나중에 PR 설명의 체크리스트가 된다.

**애매한 요구사항은 가정으로 기록한다.** 물어볼 수 있으면 물어보는 게 항상 싸다. 없으면:
```
[가정] "최근"의 기준은 30일로 해석. 설정으로 분리해 변경 가능하게 함.
```
명시한 해석은 리뷰에서 교정할 수 있다. 침묵한 해석은 릴리스 후에 발견된다.

### 먼저 확인할 것

- 이미 비슷한 게 있나 (`grep`으로 확인 — 중복 구현이 흔하다)
- 이 변경이 깨뜨릴 수 있는 기존 동작은 무엇인가
- 마이그레이션이 필요한가 (스키마 변경, 기존 데이터 처리)
- 롤백 가능한가 (되돌릴 수 없는 변경이면 단계를 나눈다)

## 2. 설계 노트 (10줄 이내)

파일을 만들기 전에 적는다.

```
- 도메인 모델: <엔티티/타입과 관계>
- 계층: <어디에 무엇을 둘지 — 기존 코드 관례를 따른다>
- 데이터 흐름: 요청 → 검증 → 서비스 → 저장 → 응답
- 에러 정책: <어떤 상황에 어떤 코드/예외>
- 안 하는 것: <명시적으로 범위 밖에 둔 것>
- 리스크: <가장 불확실한 부분 1개>
```

"안 하는 것"이 중요하다. 범위를 스스로 그으면 미구현이 결함이 아니라 판단이 된다.
리스크가 큰 부분은 여기서 팀에 한 줄 물어보는 게 이틀 뒤 되돌리는 것보다 싸다.

기존 코드베이스라면 여기서 `explore`을 먼저 실행해 관례를 파악한다.

## 3. 수직 슬라이스로 구현

계층별로 만들지 않는다(모델 전부 → 서비스 전부 → 컨트롤러 전부 = 마지막까지 아무것도 동작 안 함).
**가장 단순한 시나리오 하나를 끝에서 끝까지** 관통시킨다.

```
슬라이스 1: 정상 케이스 1개가 요청→응답까지 동작 (하드코딩 허용)
슬라이스 2: 실제 저장/조회 연결
슬라이스 3: 검증·에러 처리
슬라이스 4: 나머지 요구사항 하나씩
```

각 슬라이스 끝마다 **실행해서 동작을 확인**하고 커밋한다. 커밋 메시지가 작업 로그가 된다.
화면에 렌더링되는 변경이면 `browser`로 확인한다 — 눈으로 보는 것보다 빠르고 콘솔 에러를 놓치지 않는다.
```bash
git add -A && git commit -m "feat: 사용자 등록 정상 흐름 관통"
```

수직 슬라이스의 실질적 이득: 슬라이스 1에서 통합 지점의 문제(인증, 직렬화, 설정)가 즉시 드러난다.
이 문제들을 마지막 날에 발견하면 일정이 무너진다.

AI에게 각 슬라이스를 맡길 때는 `pair`의 사이클을 그대로 쓴다.

## 4. 테스트 — 요구사항 표와 1:1로

테스트 개수를 늘리는 게 목표가 아니다. **요구사항마다 최소 1개**가 목표다.

우선순위:
1. 요구사항 표의 각 필수 항목
2. 에러·거부 경로 (가장 자주 비는 곳이고, 실제 장애의 대부분이 여기서 온다)
3. 경계값 (빈 입력, 최대값, 중복)
4. 통합 테스트 1개 (전체 흐름 관통)

테스트 이름을 요구사항 문장으로 쓴다. 그러면 테스트 목록이 곧 명세가 되고,
6개월 뒤 이 코드를 고칠 사람이 무엇을 지켜야 하는지 알 수 있다.

```java
@Test void 중복된_이메일이면_409를_반환한다() { ... }
```
```typescript
it('중복된 이메일이면 409를 반환한다', () => { ... });
```

구체적인 작성 패턴과 프레임워크별 예시는 `references/test-strategy.md`.

**커버리지 숫자를 목표로 삼지 않는다.** 요구사항 표가 전부 ☑이면 충분하다.

## 5. 다듬기

- 이름: 도메인 용어로. 약어·`data`·`temp`·`result2` 제거
- 중복: 3번 반복되면 추출. 2번은 그냥 둔다
- 함수 길이: 화면을 넘기면 쪼갠다
- 죽은 코드·디버그 로그·주석 처리된 코드 제거
- 매직 넘버를 상수로
- 린터·포매터 실행

```bash
npm run lint -- --fix && npx tsc --noEmit && npm test
./gradlew spotlessApply build 2>/dev/null || ./gradlew build
```

**동작하는 코드를 리팩터링으로 깨뜨리는 것이 최악이다.** 각 리팩터링 후 테스트를 돌린다.
그리고 리팩터링 커밋과 기능 변경 커밋을 섞지 않는다 — 섞이면 리뷰어가 무엇이 동작 변경인지 가릴 수 없다.

## 6. PR 작성

`references/pr-description.md`의 형식을 쓴다. 최소 구성:

- 무엇을 왜 바꿨는지 (2~3문장)
- 요구사항 충족 표 (1단계 표에 상태 채운 것)
- 설계 판단과 근거 (리뷰어가 물어볼 것을 미리 답한다)
- 명시한 가정
- 리뷰어가 집중해서 볼 지점
- 미구현·후속 작업

**리뷰어가 물어볼 질문을 미리 답해두면 리뷰 왕복이 절반으로 줄어든다.**
PR 설명을 쓰는 10분이 리뷰 대기 하루를 아낀다.

## 시간 배분 (하루 단위 작업 기준)

| 구간 | 비율 | 하는 일 |
|---|---|---|
| 요구사항 표 + 설계 노트 | 20% | 코드 안 씀 |
| 슬라이스 1~2 (관통) | 25% | 정상 흐름 동작 |
| 슬라이스 3~n | 30% | 검증·에러·나머지 기능 |
| 테스트 보강 | 15% | 요구사항 표 전부 ☑ |
| 다듬기 + PR | 10% | `review` 실행 |

여러 날에 걸치는 작업이면 같은 비율을 유지하되, **매일 끝에 동작하는 상태로 커밋**한다.

## 흔한 실패

| 실패 | 결과 |
|---|---|
| 요구사항을 표로 안 만들었다 | 항목 누락. 가장 흔하고 가장 늦게 발견된다 |
| 계층별로 구현했다 | 마감까지 아무것도 동작 안 함, 통합 문제를 늦게 발견 |
| 정상 경로만 테스트 | 장애는 에러 경로에서 난다 |
| 과설계 (필요 없는 추상화, 인터페이스, 팩토리) | 리뷰가 길어지고 유지 비용이 남는다 |
| 기존 코드 관례 무시 | 리뷰 왕복 증가 |
| 커밋 1개로 500줄 | 리뷰 불가. 되돌릴 단위도 없다 |
| PR 설명 없음 | 리뷰어가 의도를 추측하고, 틀린 지적이 돌아온다 |

**과설계는 미완성만큼 비싸다.** 요구사항에 없는 확장성을 위한 추상화는 넣지 않는다.
"나중에 필요할 것 같아서"는 근거가 아니다. 필요해질 때 추출하는 편이 항상 쉽다.
