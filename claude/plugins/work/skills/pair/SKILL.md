# AI Pair Loop

AI가 코드를 쓰는 속도는 사람이 검증하는 속도를 항상 앞선다.
그래서 병목은 생성이 아니라 **검증**이고, 규율 없이 진행하면 "동작하지만 아무도 설명할 수 없는 코드"가 쌓인다.

이 스킬을 켰다면 아래 루프를 사이클 단위로 돈다. 한 사이클은 **변경 하나**를 다룬다.

## 루프

### 1. RESTATE — 무엇을 만드는지 확정한다

코드를 쓰기 전에 작업을 내 말로 재진술한다. 티켓 문장을 옮기는 게 아니라 실행 가능한 형태로.

- 입력·출력, 성공 조건, 명시되지 않은 것
- 이 변경이 **건드리지 않아야 할 것** (기존 동작, 다른 호출부)
- 엣지케이스 최소 3개: 빈 값 / 경계 / 중복·null

애매한 지점은 가정으로 못 박고 기록한다. 나중에 PR 설명에 그대로 들어간다.
```
[가정] "최근"의 기준은 30일. 설정으로 분리해 변경 가능하게 함.
```

### 2. PLAN — 어디를 어떻게 건드릴지 먼저 적는다

파일을 열기 전에 3줄.
```
- 수정할 지점: <파일:함수>
- 접근: <무엇을 어떻게>
- 안 하는 것: <범위 밖으로 둔 것>
```

기존 코드베이스라면 여기서 `explore`을 먼저 돌린다. **관례를 모르고 쓴 코드는 리뷰에서 되돌아온다.**

접근법이 두 개 이상이면 트레이드오프를 한 줄로 비교하고 고른 이유를 남긴다. 이 한 줄이 나중에 "왜 이렇게 했어?"의 답이 된다.

### 3. PROMPT — 좁은 요청 하나

한 요청 = 한 목적. `references/prompt-patterns.md`의 템플릿을 쓴다.

- 나쁨: "이 기능 만들어줘" (실패 지점을 추적할 수 없다)
- 좋음: "아래 시그니처를 유지하면서 `resolveWindow`만 구현. 입력 최대 1e5, 외부 라이브러리 추가 금지."

**시그니처는 내가 정한다.** AI가 시그니처를 바꾸면 호출부가 조용히 어긋나고, 그 변경이 어디까지 퍼졌는지 추적하는 비용이 구현 비용을 넘는다.

무엇을 맡기고 무엇을 직접 쓸지는 `references/delegation-boundaries.md` 참고.

### 4. VERIFY — 받은 즉시 깨본다

읽고 넘기지 않는다. `references/verification-gates.md`의 게이트를 순서대로 통과시킨다.

최소한:
- **존재 검증** — 호출한 API·옵션·패키지가 실제로 있는가 (환각 탐지)
- **계약 검증** — 시그니처·null 정책·부수효과가 기존 코드와 일치하는가
- 예제 하나 dry run
- 반례 후보 3개 실행
- 복잡도 확인

환각 API는 타입 체커나 컴파일러가 대부분 잡는다. **그래서 게이트 0을 자동화한다.**
```bash
npx tsc --noEmit          # 30초, 가장 값싼 전체 점검
./gradlew build -x test   # 컴파일만
```

### 5. COMMIT — 사이클을 닫는다

동작을 확인했으면 커밋한다. 사이클마다 커밋하면:
- 되돌릴 지점이 생긴다 (다음 사이클에서 깨졌을 때 `git stash`로 30초에 원인을 가른다)
- 커밋 메시지가 작업 로그가 된다
- diff가 작아서 리뷰가 가능해진다

```bash
git add -A && git commit -m "feat: 윈도우 해석 로직 추가"
```

그리고 1번으로 돌아간다.

## 사이클 크기

한 사이클은 **커밋 하나 크기**로 유지한다. 기준:
- 변경 파일 3개 이내
- diff 200줄 이내
- 한 문장으로 설명 가능

이보다 커지면 쪼갠다. 큰 사이클은 실패했을 때 원인을 가릴 수 없어서, 결국 전부 되돌리고 다시 하게 된다.

## 막혔을 때: 10분 룰

같은 문제에 10분 이상 진전이 없으면 **접근법을 버리고 2번으로 돌아간다.**
AI에게 같은 요청을 표현만 바꿔서 다시 보내는 건 진전이 아니다. 세 번째 시도에서 다른 답이 나올 확률은 낮다.

돌아갈 때 확인할 것:
- 문제를 잘못 이해했나 (1번으로)
- 접근 자체가 틀렸나 (다른 접근)
- 전제가 틀렸나 (`explore`으로 실제 코드 확인)

## 설명 가능성 규칙

**설명할 수 없는 코드는 머지하지 않는다.**

머지 전에 모든 변경 라인에 대해 답할 수 있어야 한다.

1. 이 라인이 왜 필요한가
2. 지우면 무슨 일이 생기는가

답을 못하는 라인이 있으면 둘 중 하나를 한다: 이해하거나, 내가 이해하는 형태로 다시 쓴다.
**이해되는 O(n log n)이 이해 안 되는 O(n)보다 낫다.** 6개월 뒤 그 코드를 고칠 사람은 나다.

## 하지 말 것

| 안티패턴 | 실제로 생기는 비용 |
|---|---|
| 검증 없이 붙여넣기 | 환각 API가 런타임까지 살아남는다 |
| 한 요청에 요구사항 5개 | 어디가 틀렸는지 추적 불가 → 전부 되돌림 |
| 사이클 없이 30분 연속 생성 | diff가 리뷰 불가 크기로 커진다 |
| 동작 이유를 모른 채 다음 단계 | 다음 버그를 고칠 근거가 없다 |
| AI 출력의 변수명·구조 방치 | 코드베이스 일관성이 깨지고 리뷰가 길어진다 |
| 같은 프롬프트 재시도 반복 | 시간만 소모. 2번으로 돌아가는 게 빠르다 |
