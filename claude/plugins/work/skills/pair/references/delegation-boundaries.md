# 위임 경계 — 맡길 일과 직접 할 일

AI를 어디에 쓸지는 능력 문제가 아니라 **검증 비용** 문제다.
검증이 값싼 작업은 맡기고, 검증이 생성보다 비싼 작업은 직접 한다.

## 맡겨도 되는 것 (검증이 값싸다)

| 작업 | 검증 방법 |
|---|---|
| 보일러플레이트, 반복 구조 | 컴파일 + 눈으로 패턴 확인 |
| 순수 함수 구현 (입출력이 명확) | 테스트 케이스 몇 개 |
| 타입·인터페이스 정의로부터 구현 | 타입 체커 |
| 테스트 케이스 확장 (경계값·반례) | 실행하면 바로 안다 |
| 기계적 리팩터링 (이름 변경, 추출) | 기존 테스트 전체 통과 |
| 정규식, SQL, 빌드 설정 문법 | 실제로 실행 |
| 문서·주석·PR 설명 초안 | 읽으면 안다 |
| 낯선 API의 사용 예 | 공식 문서와 대조 (환각 주의) |
| 에러 메시지 해석, 스택트레이스 요약 | 원문과 대조 |

이 목록은 공통점이 있다. **틀렸을 때 즉시, 자동으로 드러난다.**

## 직접 해야 하는 것 (검증이 생성보다 비싸다)

| 작업 | 왜 |
|---|---|
| 요구사항 해석·범위 결정 | 틀린 방향으로 완벽하게 구현하는 게 최악이다 |
| 데이터 모델·스키마 설계 | 바꾸는 비용이 가장 크다. 마이그레이션이 따라온다 |
| 공개 API·시그니처 결정 | 호출부 전체에 퍼진다 |
| 트랜잭션·동시성 경계 | 틀려도 테스트를 통과하고, 프로덕션에서만 터진다 |
| 에러 처리 정책 | 일관성이 핵심이고 AI는 파일마다 다르게 쓴다 |
| 보안 관련 판단 (인증, 권한, 입력 신뢰) | 틀린 코드가 정상 동작한다 |
| 성능 트레이드오프 결정 | 측정 없는 최적화 제안을 그대로 받으면 복잡도만 늘어난다 |
| 무엇을 **안 만들지** 결정 | AI는 요청하지 않은 것도 만든다 |

핵심 기준: **틀렸을 때 조용히 넘어가는 작업은 직접 한다.**

## 특히 위험한 세 가지

### 1. 넓은 범위 리팩터링

"이 파일 전체를 정리해줘"는 diff를 리뷰 불가 크기로 만든다.
동작이 미묘하게 바뀌었는지 확인할 방법이 없고, 실제로 바뀐다.

**대신**: 한 번에 한 종류의 변경만. "중복 제거만, 동작 보존, 기존 테스트 전부 통과."
그리고 리팩터링 커밋과 기능 변경 커밋을 절대 섞지 않는다.

### 2. 있는 코드를 지우는 제안

AI는 자기가 이해하지 못한 코드를 "불필요"로 판단한다.
그 코드는 대개 6개월 전 누군가 실제 버그를 고치려고 넣은 것이다.

**대신**: 지우기 전에 `git log -S "<코드>"`로 왜 들어왔는지 확인한다.

### 3. 의존성 추가 제안

라이브러리 하나가 전이 의존성 40개를 끌고 오고, 보안 스캔·라이선스·번들 크기·업그레이드 부채가 따라온다.

**대신**: 표준 라이브러리로 되는지 먼저 확인한다. 추가한다면 왜 필요한지 PR에 한 줄 남긴다.

## 사이클 안에서의 분업

한 사이클에서 사람과 AI의 역할은 이렇게 갈린다.

```
RESTATE   사람    — 요구사항 해석은 위임하지 않는다
PLAN      사람    — 접근·범위·안 할 것 결정
PROMPT    사람    — 요청을 좁히고 제약을 건다
          AI      — 구현
VERIFY    도구    — 컴파일러·타입체커·테스트가 1차 검증
          사람    — 계약·설계·설명 가능성은 사람이 본다
COMMIT    사람    — 무엇을 커밋할지 결정
```

**VERIFY의 1차를 도구에 넘기는 것**이 가장 큰 레버리지다.
`tsc --noEmit`, `./gradlew build`, 기존 테스트 스위트를 사이클마다 돌리면 환각과 계약 위반의 대부분이 자동으로 걸러지고, 사람은 설계 판단에만 집중할 수 있다.

## 거절도 결과물이다

AI 제안을 근거와 함께 거절한 기록은 남길 가치가 있다. PR 설명이나 코드 주석에:

```
// 인자를 직접 변경하는 구현을 받았지만 호출부가 이를 기대하지 않아
// 새 배열을 반환하는 형태로 바꿨다.
```

이런 한 줄이 리뷰 시간을 줄이고, 나중에 같은 판단을 반복하지 않게 한다.
