# 프롬프트 템플릿

좋은 요청의 공통점: **범위가 좁고, 제약이 명시되고, 검증 기준이 붙어 있다.**

## 1. 구현 요청

```
[컨텍스트] <파일/함수/기존 코드>
[목표] <함수 하나>만 구현.
[시그니처] 유지: function foo(a: string[], k: number): number
[제약] 시간 O(n), 외부 라이브러리 금지, 입력 최대 1e5
[금지] 다른 함수 수정 금지, 주석 금지
[출력] 코드만. 설명은 코드 뒤에 3줄 이내.
```

핵심: **시그니처를 내가 정한다.** AI가 시그니처를 바꾸면 호출부가 조용히 어긋나고, 그 변경이 어디까지 퍼졌는지 추적하는 비용이 구현 비용을 넘는다.

## 2. 코드 이해 요청 (낯선 코드베이스)

```
아래 코드에서 다음만 답해라. 추측은 "추측"이라고 표시.
1) 이 함수의 입력·출력 계약
2) 호출되는 곳 (추측이면 표시)
3) 상태를 변경하는 지점 (mutation, I/O, 전역)
4) 명시되지 않은 전제 조건
코드 수정 제안은 하지 마라.
```

"수정 제안 금지"를 넣는 이유: 이해 단계에서 AI가 리팩터링을 시작하면 원본 의도를 잃는다.

## 3. 디버깅 요청

증상만 던지지 않는다. **관찰 사실 + 이미 배제한 것**을 함께 준다.

```
[증상] 입력 [1,1,2]에서 기대 2, 실제 3
[정상 동작] [1,2,3] → 3 (통과)
[이미 배제] 파싱 문제 아님 (파싱 후 로그 확인함)
[가설] 중복 처리에서 카운트가 두 번 증가하는 듯
질문: 위 가설을 검증할 최소 실험 3개를 제안해라. 수정 코드는 아직 주지 마라.
```

"수정 코드는 아직 주지 마라"가 결정적이다. 원인을 모른 채 받은 패치는 증상만 가리고 다른 버그를 만든다. 리뷰에서 "왜 이렇게 고쳤어?"에 답할 근거도 남지 않는다.

## 4. 반례 생성 요청

```
아래 구현을 깨뜨리는 입력을 찾아라. 고치지는 마라.
경계값, 빈 입력, 중복, 음수, 오버플로, 정렬 안 된 입력, 유니코드를 각각 검토.
각 후보마다: 입력 / 기대값 / 예상 실제값.
```

## 5. 복잡도·성능 검토 요청

```
이 함수의 시간·공간 복잡도를 라인별 근거와 함께 계산해라.
n=1e5, n=1e6에서 예상 실행 시간을 추정해라.
가장 비싼 라인 하나만 지목해라.
```

## 6. 리팩터링 요청 (동작 보존)

```
동작을 절대 바꾸지 말고 다음만 해라: <중복 제거 / 이름 개선 / 조기 반환>
기존 테스트가 전부 통과해야 한다.
변경한 부분마다 왜 안전한지 한 줄로 근거를 붙여라.
```

## 7. 설명 요구 (머지 전 필수)

AI가 준 코드를 그대로 머지할 참이면 이걸 먼저 통과시켜라.

```
이 코드를 주니어에게 설명하듯 5줄로 요약해라.
그리고 이 코드가 틀릴 수 있는 조건 2개를 스스로 지목해라.
```

내가 이 5줄을 내 말로 재현할 수 있으면 머지 가능, 못 하면 이해하거나 다시 쓴다.

## 안티패턴

| 안티패턴 | 실제 비용 | 고친 형태 |
|---|---|---|
| "이 티켓 해줘" + 티켓 전문 붙여넣기 | 범위가 무한정 넓어져 diff가 리뷰 불가 크기가 됨 | RESTATE 후 함수 단위로 쪼개서 요청 |
| "안 돼요, 고쳐줘" | 원인 없이 증상만 가린 패치를 받는다 | 증상·기대·배제 사실을 명시 |
| 한 프롬프트에 기능 5개 | 실패 지점 추적 불가 | 기능 1개씩 순차 요청 |
| "더 좋게 만들어줘" | 판단 기준이 없어 통제 불가 | 개선 축을 하나 지정 (성능/가독성/에러처리) |
| AI 출력 그대로 머지 | 6개월 뒤 아무도 고칠 수 없다 | 7번 설명 요구를 통과시킨 뒤 다듬어 머지 |
