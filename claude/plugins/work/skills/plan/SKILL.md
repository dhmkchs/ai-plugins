# Jira Task Plan

플랜은 문서가 아니라 **실행 가능한 상태 기계**다.
`start`가 이걸 읽어 진행하고, 중단돼도 이어받고, `pr`가 이걸로 PR 본문을 만든다.
그래서 플랜의 품질이 이후 전부를 결정한다.

## 1. 티켓 번호 확보

순서대로 시도한다. 물어보는 건 마지막이다.

1. 인자로 받은 값 (`/work:plan PROJ-123`)
2. 현재 브랜치명에서 추출 (`feature/PROJ-123-...` → `PROJ-123`)
3. 사용자에게 묻는다. 이때 후보를 함께 보여준다:
   `searchJiraIssuesUsingJql: assignee = currentUser() AND statusCategory != Done ORDER BY updated DESC`

이미 `.claude/plans/<TICKET>.md`가 있으면 **덮어쓰지 않는다.** 보여주고 묻는다:
이어서 진행할지(`start`), 다시 계획할지, 다른 티켓인지.

## 2. 티켓을 끝까지 읽는다

```
getJiraIssue                    본문·상태·담당자·라벨·컴포넌트
                                → 댓글과 첨부, 링크된 이슈까지 포함해 조회
getJiraIssueRemoteIssueLinks    연결된 PR·문서
```

**댓글에 진짜 요구사항이 있는 경우가 많다.** 본문만 읽고 계획하면 절반을 놓친다.
링크된 이슈(Blocks/Depends)가 있으면 그 상태도 확인한다 — 선행 티켓이 안 끝났으면 지금 시작하면 안 된다.

읽고 나서 **요구사항을 표로 분해한다.** 문장 하나가 행 하나다.

```
| # | 요구사항 (티켓 원문 인용) | 필수 | 검증 방법 | 상태 |
```

티켓에 없지만 필요한 게 보이면 **가정으로 기록하고 사용자에게 확인**한다. 조용히 추가하지 않는다.
애매한 게 셋 이상이면 계획을 멈추고 티켓을 먼저 다듬는 게 빠르다.

## 3. 코드베이스를 정찰한다

`explore` 스킬의 절차를 실행하고 결과를 플랜에 **임베드**한다.
여기서 찾은 것을 적어두면 `start`가 같은 탐색을 반복하지 않는다. 이게 이 플랜의 실질적 가치다.

최소한 담을 것:
- 수정 지점 (`파일:라인`)과 그 함수의 계약 (입력/출력/부수효과)
- 호출부 개수와 위치 — **5곳 이상이면 시그니처를 바꾸지 않는 설계를 먼저 검토**
- 테스트 기준선 (`N passed / M failed`) — 지금 깨진 게 있으면 내 탓이 되기 전에 기록
- 코드베이스 관례 (에러 처리·로깅·테스트 스타일)
- 빌드·테스트·실행 명령

## 4. 수직 슬라이스로 쪼갠다

계층별로 쪼개지 않는다. **각 슬라이스는 끝에서 끝까지 동작하고, 커밋 하나 크기다.**

슬라이스 기준:
- 변경 파일 3개 이내, diff 200줄 이내
- 한 문장으로 설명 가능
- **완료 조건이 검증 가능** — "구현한다"가 아니라 "이 명령이 통과한다"

```
- [ ] S1 정상 흐름 관통 (하드코딩 허용)
      대상: src/controller/UserController.java, src/service/UserService.java
      테스트: UserApiTest — 정상 가입이면 201 + Location 헤더
      완료: curl -X POST localhost:8080/users -d '{...}' → 201
      커밋:
```

슬라이스가 6개를 넘으면 티켓이 너무 크다. **티켓 분할을 제안한다.**

각 슬라이스에 검증 수단을 붙인다. 화면이 바뀌면 `browser`, 로직이면 테스트 명령.

**각 슬라이스에 `테스트:` 줄을 적는다.** 그 슬라이스가 추가할 유닛 테스트를 행위 문장으로 나열한다 —
`start`가 이 줄을 보고 구현과 함께 테스트를 쓴다. 여기가 비어 있으면 테스트가 마지막으로 밀리고, 대개 안 써진다.
요구사항 표의 `검증 방법` 칸과 같은 이름을 쓰면 요구사항 ↔ 테스트가 1:1로 추적된다.
유닛 테스트가 의미 없는 슬라이스(설정·마이그레이션·순수 배선)는 `테스트: 없음 — <대체 검증>`으로 명시한다.
테스트를 어떻게 도출할지는 `test` 스킬.

## 5. 플랜 파일을 쓴다

`.claude/plans/<TICKET>.md`에 저장한다. 형식은 `references/plan-format.md`가 정본이다.
**front-matter는 반드시 넣는다** — `start`·`pr`·`status`가 이걸로 상태를 읽는다.

`.work/`가 처음이면 `.gitignore` 처리를 묻는다.
**커밋을 권한다** — 플랜이 리뷰어에게 맥락을 주고, 중단된 작업을 남이 이어받을 수 있다.

## 6. 품질 게이트

저장 전에 스스로 점검한다. 하나라도 아니면 고친다.

- [ ] 모든 요구사항이 최소 한 슬라이스에 매핑됐다
- [ ] 각 슬라이스의 완료 조건이 **실행 가능한 명령**이다
- [ ] 각 슬라이스에 `테스트:` 줄이 있다 (없으면 없는 이유와 대체 검증이 적혀 있다)
- [ ] 정찰 노트에 실제 파일 경로가 있다 (추측이 아니라 확인한 것)
- [ ] "범위 밖"이 비어있지 않다
- [ ] 리스크가 최소 하나 적혀 있다 (없으면 아직 안 본 것이다)
- [ ] 되돌릴 수 없는 변경(마이그레이션·데이터 삭제)이 있으면 별도 슬라이스로 분리됐다

## 7. 마무리

플랜 요약을 보여주고 승인받는다. 승인 후:
- 사용자가 원하면 `addCommentToJiraIssue`로 플랜 요약을 티켓에 남긴다 (전문이 아니라 요약 + 슬라이스 목록)
- **Jira 상태는 여기서 바꾸지 않는다.** 실제 착수는 `start`가 한다

```
PROJ-123 플랜 작성됨 → .claude/plans/PROJ-123.md
슬라이스 4개 / 요구사항 6개 / 리스크 1건
다음: /work:start PROJ-123
```

## 하지 말 것

| 안티패턴 | 실제 비용 |
|---|---|
| 정찰 없이 계획 | 존재하지 않는 파일을 대상으로 잡는다 |
| 계층별로 쪼개기 | 마지막까지 아무것도 동작 안 함 |
| 완료 조건이 "구현한다" | 끝났는지 판정 불가 |
| 티켓 댓글 안 읽기 | 요구사항 절반 누락 |
| 기존 플랜 덮어쓰기 | 진행 이력이 사라진다 |
| 슬라이스 10개짜리 플랜 | 티켓이 너무 크다는 신호 — 쪼갠다 |
