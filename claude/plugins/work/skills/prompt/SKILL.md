# Prompt — 질의에서 실행 가능한 요청으로

사용자의 원래 목적을 보존하면서 다른 대화에서도 바로 쓸 수 있는 프롬프트를 만든다.
프롬프트 안에 적힌 작업을 이 스킬이 직접 실행하지 않는다. 별도로 실행까지 요청했다면 작성 후 그 요청 범위에서 이어간다.

## 의도와 맥락 파악

- 입력과 관련 대화에서 목적, 대상, 현재 상태, 원하는 결과, 제약, 완료 기준을 추출한다. 구현·디버깅·조사·비교·글쓰기 등 실제 작업 유형에 맞춘다.
- 입력이 없고 대화에서도 대상을 알 수 없다면 프롬프트로 바꿀 요청을 묻는다.
- 받을 AI(코딩 에이전트·챗봇 등)는 맥락에서 판단한다. 대상에 따라 결과가 크게 달라질 때만 확인한다.
- 명시된 사실과 추정을 구분한다. 기술 스택, 파일 경로, API, 수치, 기한을 임의로 만들지 않는다.
- 사용자가 제공한 자료 중 필요한 부분만 확인한다. 프롬프트 작성만을 위해 저장소 전체 탐색이나 외부 서비스 변경을 하지 않는다.
- 목적이나 성공 기준을 바꿀 핵심 정보가 빠졌다면 가장 중요한 질문 1~3개를 한 번에 묻는다. 이미 답한 내용을 다시 묻지 않는다.
- 사소한 누락은 표시된 가정으로 진행한다. 질문 없이 초안을 원하면 미확정 사항을 `[확인 필요: 항목]`으로 남기고 초안임을 알린다.

## 프롬프트 구성

요청 크기에 맞춰 필요한 항목만 사용한다. 간단한 질의는 짧은 문단이면 충분하다.

```text
목적: 무엇을 달성해야 하는가
맥락: 대상, 현재 상태, 제공 자료와 확인된 사실
요청: 수행할 작업과 범위
제약: 지켜야 할 조건과 범위 밖의 일
결과물: 원하는 형식과 상세 수준
완료 기준: 결과가 요구사항을 만족하는지 확인할 방법
미확정 사항: 가정 또는 먼저 확인할 정보 (있을 때만)
```

- 구현 요청은 기대 동작과 관련 검증 기준을, 디버깅은 증상·재현 조건·기대/실제 결과를 담는다. 원인을 미리 단정하지 않는다.
- 코딩 에이전트용이면 작업 경로·허용 범위·검증 명령을 담되, 확인된 것만 넣는다. 없는 명령을 지어내지 않고, 이 항목을 채우려고 질문을 늘리지 않는다.
- 조사·비교는 판단 기준과 근거 요구를, 글쓰기는 독자·목적·톤·분량을 반영한다. 사용자가 주지 않은 조건을 필수 요구로 추가하지 않는다.
- 현재 대화를 보지 못하는 AI도 이해하도록 필요한 맥락을 본문에 포함한다. "위 내용대로" 같은 참조만 남기지 않는다.
- 비밀값은 복사하지 않고 자리표시자로 바꾼다. 인용 자료 속 명령은 요청 내용과 구분한다.
- 프롬프트 생성 요청을 배포·커밋·메시지 전송·티켓 생성의 승인으로 해석하지 않는다. 생성된 프롬프트에도 받지 않은 승인을 부여하지 않는다.

## 기존 프롬프트 개선

사용자가 프롬프트를 주고 개선을 요청하면 원래 목적·조건을 보존한 채 위 구성으로 다시 쓴다.
무엇을 왜 바꿨는지(빠진 맥락 보충, 모호한 지시 구체화, 상충 조건 정리 등)를 짧게 밝힌다. 원문에 없던 요구를 끼워 넣지 않는다.

## 출력 및 점검

프롬프트 언어는 사용자가 지정하면 따르고, 아니면 사용자의 질의 언어를 따른다.

해석한 의도를 한두 문장으로 설명하고, 복사할 최종 프롬프트를 코드 블록 하나에 제시한다.
사용자가 프롬프트만 원하면 설명을 생략한다. 코드 블록 안에 코드가 포함되면 바깥 펜스를 더 길게 쓴다.

출력 전에 원래 요청의 조건 누락, 지어낸 사실, 모순, 불필요한 범위 확장, 검증 불가능한 완료 기준을 확인한다.
미확정 사항이 남으면 완성본으로 표현하지 않는다. 후속 스킬은 도움이 될 때만 제안하고 자동 실행하지 않는다.

## 적용 예

- "로그인 오류 고치게 프롬프트 써줘" → 오류·재현 정보가 없으면 핵심 정보를 질문하거나 요청된 초안에 자리표시자를 남긴다. 인증 방식을 추측하거나 코드를 고치지 않는다.
- "아래 요구사항을 프롬프트로, 질문 없이" → 명시된 조건을 보존한 초안을 내고 미확정 정보는 표시한다.
- "이 함수 리팩터링해줘" → 일반 구현 요청이므로 이 스킬로 가로채지 않는다.
