# Refactor — 얕은 모듈을 깊게

리팩터링의 실패는 대개 **무엇이 나아졌는지 말할 수 없는 것**으로 끝난다.
파일을 옮기고 이름을 바꾸고 나서 "깔끔해졌다"고 하면, 다음 사람은 그 판단을 검증할 수 없고
같은 자리를 또 갈아엎는다.

이 스킬은 세 가지를 강제한다.

1. **같은 말을 쓴다** — 구조를 부르는 어휘를 고정한다
2. **판정한다** — "좋아 보인다"가 아니라 예/아니오가 나오는 검사를 돌린다
3. **센다** — 고치기 전후로 관측 가능한 지표를 남긴다

동작을 바꾸지 않는 것이 전제다. 동작이 바뀌면 리팩터링이 아니라 기능 변경이고, `feature`로 간다.

## 정지점 — 혼자 끝까지 가지 않는다

이 스킬은 **두 번 멈춘다.** 멈추지 않으면 아무도 요청하지 않은 재설계를 계속하게 된다.

| 정지점 | 무엇을 내놓고 멈추나 |
|---|---|
| **2단계 끝** | 후보 목록 + 각 후보의 삭제 테스트 결과와 before 지표. **어느 것을 할지 사용자가 고른다** |
| **4단계 끝** | 인터페이스 2안 이상 + 내 추천. **어느 안으로 갈지 사용자가 고른다** |

**후보를 스스로 골라 바로 실행으로 넘어가지 않는다.** 무엇이 진짜 마찰인지는 코드가 아니라
그 코드로 일하는 사람이 안다. 지표는 후보를 좁혀줄 뿐 결정하지 않는다.

한 번에 **후보 하나**만 진행한다. "이왕 하는 김에"로 범위를 넓히지 않는다 —
커진 리팩터링은 리뷰가 불가능해지고 되돌릴 수도 없다.

## 어휘 — 이 말들만 쓴다

구조 이야기를 할 때 **아래 용어를 그대로** 쓴다. 같은 것을 여러 이름으로 부르면
스킬 사이 인수인계가 새고, 리뷰에서 서로 다른 것을 이야기하게 된다.

| 용어 | 뜻 | 쓰지 않을 말 |
|---|---|---|
| **모듈** | 인터페이스와 구현을 가진 것. 함수·클래스·패키지·슬라이스 어느 규모든 | 컴포넌트, 서비스, 유닛 |
| **인터페이스** | 호출자가 올바르게 쓰기 위해 **알아야 하는 전부** — 시그니처 + 불변식 + 호출 순서 + 에러 모드 + 필요한 설정 | API, 시그니처 (타입 표면만 가리켜 너무 좁다) |
| **깊이** | 인터페이스 한 단위를 배워서 쓸 수 있는 동작의 양. **얕음** = 인터페이스가 구현만큼 복잡 | — |
| **seam** | 그 자리를 고치지 않고 동작을 바꿔 끼울 수 있는 지점. 인터페이스가 **놓이는 위치** | 경계 (DDD bounded context와 겹친다) |
| **어댑터** | seam에 꽂혀 인터페이스를 만족시키는 구체물. 역할이지 내용물이 아니다 | 구현체 (구현과 어댑터는 다르다) |

**깊이를 "구현 줄 수 ÷ 인터페이스 줄 수"로 재지 않는다.** 그러면 구현을 부풀리는 게 이득이 된다.
깊이는 **호출자가 배우는 양 대비 얻는 동작의 양**이다.

## 판정 테스트 — 세 가지, 예/아니오가 나온다

### 1. 삭제 테스트 — 이 모듈은 값을 하는가

이 모듈을 지웠다고 상상한다. **복잡도가 사라지나, 호출부로 번지나.**

```bash
# 후보 모듈의 호출부를 센다
grep -rn "from ['\"].*formatMoney" src/ --include=*.ts | grep -v "src/money/"
```

| 결과 | 판정 |
|---|---|
| 호출부 N곳이 **각자 같은 로직을 다시 써야 한다** | 값을 한다. 남긴다 (복잡도가 여기 모여 있다) |
| 호출부가 **다음 계층을 직접 부르면 그만이다** | 통과 계층이다. 지운다 |
| 호출부가 1곳뿐이다 | 인라인 후보. 모듈로 있을 이유가 아직 없다 |

`review`의 「1인용 래퍼」가 정확히 세 번째 경우다. 삭제 테스트가 그 판정 근거다.

### 2. 어댑터 2개 규칙 — 이 seam은 진짜인가

**어댑터가 하나면 가상의 seam이고, 둘이면 진짜 seam이다.**
무언가가 실제로 달라지지 않는 자리에 인터페이스를 끼우면 그건 그냥 간접층이다.

프로덕션 구현 + 테스트용 대역 = 2개면 정당하다. 프로덕션 구현 하나뿐이면 seam을 만들지 않는다.

### 3. 인터페이스가 곧 테스트 표면

호출자와 테스트는 **같은 seam을 지난다.** 테스트가 인터페이스 **너머**를 만져야 한다면
모듈 모양이 틀린 것이다. 내부를 열어주는 게 아니라 모듈을 다시 가른다.

```bash
# 테스트가 내부 파일을 직접 import 하면 seam 이 새고 있다
grep -rn "from ['\"].*/internal/\|/impl/" --include=*.test.ts --include=*.spec.ts src/
```

## 1단계: 범위 — 자주 바뀌는 곳만 본다

**깊게 만드는 작업은 그 모듈이 앞으로 또 바뀔 때만 본전을 뽑는다.**
1년째 아무도 안 건드린 코드를 예쁘게 만드는 건 순손실이다. 볼 곳부터 정한다.

사용자가 대상을 지목했으면 그걸 쓰고 아래를 건너뛴다. 아니면 이력에서 찾는다.

```bash
# 최근 변경이 몰린 파일 = 지금 살아 있는 부분
git log --name-only --pretty=format: -200 | sort | uniq -c | sort -rn | head -20

# 그 파일들이 함께 바뀌는가 — 같이 바뀌면 한 모듈이어야 할 것이 흩어진 신호다
git log --name-only --pretty=format:"%h" -100 | awk 'NF' | head -60
```

**여러 파일이 매번 같이 바뀐다면** 그 묶음이 첫 후보다. 하나의 개념이 여러 얕은 모듈로
쪼개져 있다는 뜻이고, 변경 하나가 매번 N군데를 요구한다.

기존 결정을 다시 뒤집지 않도록 `docs/adr/`를 먼저 읽는다. 후보가 ADR과 충돌하면
**마찰이 실제로 클 때만** 올리고, 올릴 때는 "ADR-0007과 충돌하지만 재검토할 값이 있다"고 명시한다.

## 2단계: 후보 판정과 before 지표

후보마다 삭제 테스트를 돌리고, **고치기 전 숫자를 남긴다.** 이게 없으면 나중에 개선을 증명할 수 없다.

```bash
M=src/order    # 대상 클러스터

# 인터페이스 표면 — 밖으로 내보내는 심볼 수
grep -rhoE "^export (const|function|class|type|interface|default) [A-Za-z0-9_]*" $M | wc -l
grep -rhoE "public [A-Za-z<>,\[\] ]+ [a-zA-Z0-9_]+\(" $M --include=*.java | wc -l   # Java

# 구현 부피
git ls-files $M | xargs wc -l | tail -1

# 호출부 — 밖에서 이 클러스터를 얼마나 알고 있나
grep -rn "from ['\"].*order" src/ --include=*.ts | grep -v "^$M" | wc -l
grep -rhoE "import .*order\.[A-Za-z0-9_]+" src/ --include=*.java | sort -u | wc -l

# 테스트
grep -rc "it(\|test(\|@Test" $M | awk -F: '{s+=$2} END {print s}'
```

| 지표 | 좋아지는 방향 |
|---|---|
| 인터페이스 표면 (export/public 수) | **↓** |
| 구현 부피 | 유지 또는 ↑ (동작이 안쪽으로 들어온 것) |
| 밖에서 import 하는 심볼 수 | **↓** — 호출자가 배울 게 줄었다 |
| 테스트가 만지는 내부 파일 수 | **0** — 인터페이스만 지난다 |
| 테스트 수 | 대개 **↓** (얕은 테스트가 사라지고 인터페이스 테스트로 대체) |

숫자가 하나도 안 움직이는 리팩터링은 **파일을 옮긴 것**이지 구조를 바꾼 게 아니다.

## 3단계: 의존성 분류 → 테스트 전략이 결정된다

후보의 의존성이 어느 종류인지가 **테스트를 어떻게 할지를 결정한다.** 추측하지 않는다.

| 분류 | 무엇 | 전략 |
|---|---|---|
| **in-process** | 순수 계산, 메모리 상태, I/O 없음 | 항상 깊게 만들 수 있다. 합치고 새 인터페이스로 직접 테스트. 어댑터 불필요 |
| **local-substitutable** | 로컬 대역이 있는 것 (PGLite, 인메모리 FS, testcontainers) | 대역이 있으면 가능. seam은 **내부**에 둔다 — 외부 인터페이스에 port를 노출하지 않는다 |
| **remote-owned** | 우리가 소유한 원격 (사내 API, 다른 서비스) | seam에 **port**를 정의. 프로덕션=HTTP 어댑터, 테스트=인메모리 어댑터. 로직은 한 모듈에 모인다 |
| **true-external** | 통제 못 하는 서드파티 (Stripe, Twilio, 카카오) | 주입받는 port + 테스트는 mock 어댑터 |

**내부 seam과 외부 seam을 구분한다.** 깊은 모듈도 내부에 seam을 가질 수 있고
자기 테스트가 그걸 쓸 수 있다. 하지만 **테스트가 쓴다는 이유로 인터페이스에 노출하지 않는다.**

## 4단계: 인터페이스를 두 번 이상 설계한다

**첫 안이 최선인 경우는 드물다.** 후보가 정해지면 인터페이스를 여러 방향으로 설계해 비교한다.

병렬 서브에이전트를 쓸 수 있으면 각각에 **다른 제약**을 준다. 같은 제약을 주면 같은 답이 셋 나온다.

| 에이전트 | 제약 |
|---|---|
| 1 | **인터페이스 최소화** — 진입점 1~3개. 진입점당 동작량 최대 |
| 2 | **유연성 최대화** — 확장·다양한 호출 방식 지원 |
| 3 | **최빈 호출자 최적화** — 가장 흔한 경우를 자명하게 |
| 4 | (해당 시) **ports & adapters** — 3단계 분류가 remote-owned/true-external일 때 |

각 안이 내놓을 것: ① 인터페이스(타입·불변식·호출 순서·에러 모드) ② 호출 예시
③ seam 뒤에 숨는 것 ④ 의존성 전략과 어댑터 ⑤ 어디서 이득이고 어디가 얇은지.

**비교는 깊이·변경이 모이는 곳·seam 위치 세 축으로 한다.** 그리고 하나를 고른다.
메뉴를 늘어놓지 않는다 — 근거를 붙여 하나를 추천하고, 좋은 조각이 섞이면 혼합안을 제안한다.

병렬 실행이 어려우면 최소 두 안을 순차로 만든다. **한 안만 만들고 진행하지 않는다.**
서브에이전트 도구는 환경마다 이름과 존재 여부가 다르다 — **없으면 순차로 간다.** 여기서 멈추지 않는다.

안을 다 만들면 **비교와 추천을 내놓고 멈춘다.** 고르는 것은 사용자다 (정지점 2).

## 5단계: 실행 — 테스트를 먼저 확보하고, 하나씩

동작이 안 바뀌는 것이 이 작업의 전제다. **그걸 보장하는 건 기존 테스트뿐이다.**

```bash
# 기준선. 여기서 초록이 아니면 리팩터링을 시작하지 않는다
npm test          # 또는 ./gradlew clean test
```

대상 영역에 테스트가 없으면 **리팩터링 전에 현재 동작을 고정하는 테스트를 먼저 쓴다.**
그 테스트는 새 인터페이스가 아니라 **현재 인터페이스**를 대상으로 한다 — 안전망이 목적이다.

- 한 번에 하나의 후보만 처리한다. 여러 개를 동시에 하면 무엇이 깨뜨렸는지 못 찾는다
- 커밋을 잘게 나눈다 (`commit`) — 되돌릴 수 있는 단위로
- 각 단계 후 테스트를 돌린다. 빨개지면 다음으로 넘어가지 않는다

## 6단계: 검증 — replace, don't layer

### 옛 테스트를 지운다

깊은 모듈의 인터페이스 테스트가 생기면, **얕은 모듈들에 붙어 있던 유닛 테스트는 폐기물이다.**
지운다. 남겨두면 세 가지가 생긴다.

- 사라진 구조에 결합된 테스트가 다음 리팩터링을 막는다
- 통과해도 아무것도 보장하지 않는다 (그 인터페이스로는 이제 아무도 호출하지 않는다)
- 테스트 수가 늘어 커버리지가 좋아 보인다 — **가짜 확신**

새 테스트는 **인터페이스에서** 쓴다. 관측 가능한 결과를 단정하고 내부 상태를 보지 않는다.
구현을 바꿨을 때 테스트도 바꿔야 한다면 그 테스트는 인터페이스 너머를 보고 있다.

### after 지표를 낸다

2단계와 **같은 명령**으로 다시 센다.

| 지표 | before | after |
|---|---|---|
| 인터페이스 표면 | 23 export | **6 export** |
| 밖에서 import 하는 심볼 | 41곳 | **12곳** |
| 구현 부피 | 480줄 | 510줄 (동작이 안으로 들어옴) |
| 테스트가 만지는 내부 파일 | 7개 | **0개** |
| 테스트 수 | 34 | 19 (얕은 테스트 21개 삭제, 인터페이스 테스트 6개 추가) |
| 전체 테스트 | 142 passed | **142 passed** (동작 불변 확인) |

**전체 테스트 결과가 같아야 한다.** 하나라도 다르면 리팩터링이 아니라 동작 변경이다.

### seam을 강제한다 — 규칙이 없으면 다시 샌다

인터페이스를 좁혀놔도 **우회하는 import를 막을 수단이 없으면 시간이 지나며 도로 새어나간다.**
사람도 에이전트도 급하면 내부 파일을 직접 가져간다. 위 지표는 **지금 이 순간의 스냅샷**일 뿐,
회귀를 막지 못한다 (`perf`의 예산 파일이 하는 역할이 여기에도 필요하다).

깊게 만든 모듈에는 **강제 수단을 함께 둔다.** 프로젝트 사정에 맞는 것 하나면 된다.

```js
// eslint.config.mjs — 인터페이스를 우회하는 import 금지 (검증됨)
export default [
```

`src/app/bad.ts`가 `../order/internal`을 가져가면 error, `../order/index`는 통과,
`src/order/` 내부끼리는 통과한다.

**어느 것도 쓸 수 없으면 그 사실을 보고에 적는다.** 강제되지 않는 seam은 다음 분기에 사라져 있다.

**"깔끔해졌습니다"로 끝내지 않는다.** 무엇이 어떻게 줄었는지 숫자로 쓴다.

## 하지 말 것

| 안티패턴 | 실제 비용 |
|---|---|
| 지표 없이 "구조가 좋아졌다" | 다음 사람이 검증 못 하고 같은 자리를 또 갈아엎는다 |
| 자주 안 바뀌는 코드 리팩터링 | 본전을 못 뽑는다. 순손실 |
| 테스트 없는 코드를 먼저 리팩터링 | 동작 불변을 보장할 수단이 없다 |
| 리팩터링과 기능 변경을 한 커밋에 | 되돌릴 수 없고 리뷰어가 못 가른다 |
| 옛 얕은 테스트를 남겨둠 | 다음 리팩터링을 막고 가짜 확신을 준다 |
| 인터페이스 안 하나만 만들고 진행 | 첫 안이 최선인 경우는 드물다 |
| 어댑터 하나짜리 seam 만들기 | 변하는 게 없는 자리의 간접층 — 복잡도만 늘린다 |
| 테스트 편의로 내부를 인터페이스에 노출 | seam이 새고, 이후 내부 변경마다 테스트가 깨진다 |
| "깊은 모듈이 좋다"로 거대 모듈 정당화 | 깊이는 인터페이스의 성질이지 크기가 아니다 |
| 여러 후보를 동시에 처리 | 무엇이 깨뜨렸는지 못 찾는다 |
| ADR이 막아둔 방향을 다시 제안 | 이미 판단이 끝난 논의를 반복한다 |
| 폴더 구조 개편을 구조 개선이라 부르기 | **모듈은 파일 시스템과 직교한다.** 폴더를 옮겨도 인터페이스가 그대로면 아무것도 안 바뀌었다 |
| 후보를 스스로 골라 실행까지 직행 | 아무도 요청하지 않은 재설계가 쌓인다. 정지점에서 멈춘다 |
| seam만 만들고 강제 수단은 안 두기 | 몇 달 뒤 우회 import로 도로 새어 원상복구된다 |

## 먹히고 있다는 신호

절차를 밟았는지가 아니라 **결과가 달라졌는지**로 본다.

- 구조 대화에서 "컴포넌트·서비스·경계"가 사라지고 **"모듈·인터페이스·seam"**이 나온다
- 제안된 추출에 대해 **삭제 테스트 통과 여부를 망설임 없이** 말할 수 있다
- seam을 제안할 때 **두 번째 어댑터의 이름이 함께** 나온다
- 인터페이스 이야기가 타입 시그니처에서 끝나지 않고 **불변식·호출 순서·에러 모드**까지 간다
- 리팩터링 PR에 before/after 숫자가 붙는다

반대로 **이 스킬이 켜졌다는 이유만으로 파일을 읽고 재설계를 시작하고 있으면** 잘못 쓰고 있는 것이다.
어휘와 판정 테스트는 참조용이고, 실행은 사용자가 후보를 고른 뒤에 시작한다.

## work 사슬 연결

- 후보 탐색 전에 코드베이스가 낯설면 `explore`부터. 이 스킬 1단계의 churn 명령은 `explore` 1단계와 같다.
- 새 테스트 작성과 옛 테스트 삭제 판단은 `test`의 규율을 따른다 (**replace, don't layer**).
- 되돌리기 비싼 판단(모듈 경계 확정, port 도입, 저장소 교체)까지 갔으면 `adr`로 남긴다.
  사용자가 후보를 **거절했고 그 이유가 하중을 받으면 그것도 ADR로** 남긴다 —
  다음 리팩터링이 같은 제안을 반복하지 않게 하는 억제 기록이다.
- 커밋은 `commit`의 원자 단위로, 푸시 전 `review`로 훑는다.
- 동작이 바뀌면 이 스킬이 아니다. `feature`(요구사항 기반) 또는 `debug`(버그)로 간다.
