# 실행 규칙

## 브랜치

```bash
# 항상 최신 base에서 딴다
git fetch origin
git switch -c feature/PROJ-123-duplicate-email origin/main

# 이미 있으면 새로 만들지 않는다
git switch feature/PROJ-123-duplicate-email
```

이름 규칙: `<prefix><TICKET>-<슬러그>`

- 슬러그는 티켓 제목을 소문자 하이픈으로. 한글 제목이면 영문 요약으로 바꾼다 (한글 브랜치명은 CI·툴에서 자주 깨진다)
- 40자를 넘기지 않는다
- prefix는 config의 `branchPrefix` (기본 `feature/`). 프로젝트 `.work/config.json` > 글로벌 `~/.work/config.json`

작업 중 base가 많이 움직였으면 중간에 리베이스한다. 마지막에 몰아서 하면 충돌이 커진다.

```bash
git fetch origin && git rebase origin/main
```

## 커밋

**슬라이스 하나 = 커밋 하나.** 예외 없다.

```bash
git commit -m "feat(PROJ-123): 이메일 정규화 및 중복 검사 추가"
```

- 티켓 키를 넣는다. Bitbucket은 커밋 메시지의 Jira 키로 티켓과 자동 연결한다
- 타입 접두사는 저장소 관례를 따른다 (`feat`/`fix`/`refactor`/`test`/`chore`).
  기존 로그를 먼저 본다: `git log --oneline -20`
- 무엇을 왜 했는지 쓴다. "수정", "업데이트", "작업"은 정보가 없다
- 리팩터링과 기능 변경을 한 커밋에 섞지 않는다
- **테스트는 그 행위를 만든 커밋에 함께 넣는다.** 테스트만 뒤에 따로 커밋하면
  되돌릴 때 구현만 남거나 테스트만 남는다

커밋 전 확인:
```bash
git diff --cached --stat        # 의도한 파일만 있는가
git status --porcelain          # 빠뜨린 게 없는가
```

## 테스트 — 슬라이스마다

**구현과 그 유닛 테스트는 같은 커밋에 들어간다.** 테스트가 없는 슬라이스는 완료가 아니다.
무엇을 어떻게 쓰는지는 `test` 스킬이 정본이고, 여기서는 실행 규율만 다룬다.

순서:

```bash
# 1. 버그 수정이면 테스트부터 — 수정 전에 실패를 눈으로 본다
./gradlew test --tests "*UserServiceTest.중복*"        # → FAILED (버그 때문에)

# 2. 구현

# 3. 같은 명령을 다시 — 이번엔 통과
./gradlew test --tests "*UserServiceTest.중복*"        # → 1 passed

# 4. 전체 — 기준선과 비교
./gradlew test                                          # → 148 passed (기준선 142)
```

새 기능 슬라이스는 1을 건너뛰고 구현 → 테스트 → 실행 순으로 가도 된다.
**버그 수정만은 예외가 없다.** 실패를 보지 않은 테스트는 회귀를 지킨다는 증거가 없다.

체크 규칙:

- 테스트 파일 위치·이름은 저장소 관례를 따른다 (`src/test/java/...Test.java`, `*.test.ts`, `__tests__/`)
- **새 테스트 프레임워크를 도입하지 않는다.** 러너를 바꿔야 한다고 판단되면 별도 티켓으로 제안한다
- 새로 추가한 테스트가 **정말 실패할 수 있는지** 한 번 의심한다.
  단정을 잠깐 뒤집어보거나 구현 한 줄을 되돌려서 빨개지는지 확인한다 — 항상 초록인 테스트가 가장 나쁘다
- 유닛 테스트가 의미 없는 슬라이스(설정·마이그레이션·순수 배선)는 **왜 없는지와 대체 검증을 플랜 로그에 남긴다**
- 커밋 전에 `skip`·`only`·주석 처리한 테스트가 남았는지 본다

```bash
# 커밋 전 비활성 테스트 훑기
git diff --cached | grep -nE '^\+.*(it|test|describe)\.(skip|only)|^\+.*@(Disabled|Ignore)'
```

남길 이유가 있으면 티켓 번호를 주석에 붙인다. 이유 없는 skip은 `review`가 다시 잡는다.

## 검증 — 슬라이스마다

완료 조건 명령을 **실제로 실행하고 출력을 본다.** "통과했을 것이다"로 넘어가지 않는다.

```bash
# 슬라이스 범위만 빠르게
./gradlew test --tests "*UserApiTest*"
npm test -- -t "중복 이메일"

# 그다음 전체 — 기준선과 비교
./gradlew test
npm test
```

기준선(플랜의 정찰 노트)보다 실패가 늘었으면 **그 자리에서 멈춘다.** 다음 슬라이스로 가지 않는다.

내 변경이 원인인지 30초에 가르는 법:
```bash
git stash && ./gradlew test ; git stash pop
```

화면이 바뀌는 슬라이스는 `browser`를 돌린다. 코드만 봐서는 렌더링·콘솔 에러를 알 수 없다.

## 중단과 재개

중단할 때:
1. 진행 중이던 슬라이스가 완료 조건을 통과했으면 커밋하고 체크
2. 통과 못 했으면 **커밋하지 않는다.** 대신 플랜 로그에 어디까지 했는지 남긴다
   ```
   - 2026-08-03 S2 진행 중 — UserService.register까지 수정. 정규화 위치 미결(엔티티 vs 서비스)
   ```
3. 작업 중인 변경은 그대로 두거나 `git stash push -m "PROJ-123 S2 wip"`

재개할 때:
1. 플랜의 `## 로그` 마지막 항목을 읽는다
2. `git log --oneline origin/main..HEAD`로 실제 커밋과 플랜 체크박스가 일치하는지 확인
3. **불일치하면 플랜을 실제에 맞춘다.** 실제 코드가 진실이다
4. `git stash list`에 남은 게 있는지 확인

## 슬라이스 실패 대응

| 상황 | 대응 |
|---|---|
| 완료 조건 미통과 | `debug` 절차로 전환. 원인 모른 채 다음으로 가지 않는다 |
| 테스트가 뭘 단정해야 할지 모르겠다 | 계약이 불분명한 것이다. `test` 스킬의 행위 표부터 만든다 |
| 테스트를 쓰려니 목이 5개 필요하다 | 설계 신호다. 로직을 순수 단위로 추출하고 배선은 통합 테스트로 |
| 기존 테스트가 깨졌다 | 회귀인지 의도한 명세 변경인지 먼저 가른다. 단정을 느슨하게 해서 통과시키지 않는다 |
| 10분 이상 진전 없음 | 접근을 바꾼다. 같은 프롬프트 재시도는 진전이 아니다 |
| 슬라이스가 너무 컸다 | 둘로 쪼개고 플랜을 갱신, 로그에 이유 기록 |
| 순서가 틀렸다 | 슬라이스 순서 조정, 로그에 기록 |
| 선행 티켓 필요 | `status: blocked` + 로그에 티켓 번호. 멈춘다 |
| 요구사항이 틀렸다 | 코드로 우회하지 말고 티켓을 고친다. 사용자에게 확인 |

**플랜이 틀렸다고 판단되면 플랜을 고치는 게 정상 동작이다.** 플랜을 방치하고 코드만 진행하는 게 실패다.

## 되돌리기 어려운 변경

실행 전에 승인받고, 되돌리는 방법을 함께 제시한다.

| 유형 | 승인 전에 확인할 것 |
|---|---|
| DB 마이그레이션 | 역방향 마이그레이션이 있는가. 기존 데이터가 제약을 위반하지 않는가 |
| 데이터 삭제·변경 | 백업이 있는가. 영향 건수를 먼저 세었는가 |
| 외부 API 쓰기 | 테스트 환경인가. 멱등한가 |
| 설정·시크릿 변경 | 롤백 절차가 있는가 |
| 파일 삭제 | `git log -S "<내용>"`으로 왜 들어왔는지 확인했는가 |

마이그레이션은 **항상 별도 슬라이스**로 둔다. 코드 변경과 같은 커밋에 넣으면 롤백할 때 함께 딸려간다.

## 범위 이탈 방지

작업 중 눈에 띈 것은 고치지 않고 기록한다.

```
- 2026-08-03 발견: AdminUserController에도 같은 누락. 범위 밖 → 후속 티켓
- 2026-08-03 발견: UserImportJob의 예외 처리가 빈 catch. 범위 밖 → 후속 티켓
```

작업이 끝난 뒤 이 목록을 사용자에게 보여주고 후속 티켓 생성을 제안한다 (`ticket`).
**발견한 문제를 조용히 버리지 않는다.** 기록되지 않은 발견은 없던 일이 된다.

## 진행 보고 형식

각 슬라이스가 끝날 때 한 블록.

```
S2 완료 — 이메일 정규화 + 중복 검사
  대상: UserService.java, User.java (+48 -6)
  테스트: UserServiceTest 4건 추가 (정상 / 대소문자 / 앞뒤 공백 / 중복 거부)
  검증: ./gradlew test --tests "*UserApiTest.중복*" → 2 passed
  전체: 146 passed / 0 failed (기준선 142 → 신규 4건)
  커밋: a1b2c3d
  다음: S3 409 응답 매핑
```

숫자를 넣는다. "잘 됐습니다"는 확인 가능한 정보가 아니다.
