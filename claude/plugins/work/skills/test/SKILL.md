# Unit Test

유지보수 비용을 뽑는 유닛 테스트의 기준이다. **프로젝트가 이미 쓰는 러너·단정 라이브러리 위에 얹는다 —
이 문서를 따르려고 새 테스트 프레임워크를 들이지 않는다.**

## 규칙 등급

- **MUST** — 리뷰 차단. 위반한 테스트는 머지하지 않는다
- **SHOULD** — 기본값. 벗어나려면 PR에 이유를 쓴다

규칙이 충돌하면 **믿을 수 있는 쪽**을 고른다. 좋은 테스트는 *행위가 깨졌을 때만* 깨진다.

## 절차

1~5번을 건너뛰지 않는다.

1. **관례를 먼저 읽는다.** 테스트 설정 파일과 기존 테스트 2~3개를 읽는다.
   러너, 단정 스타일, 파일 위치·이름 규칙, 공용 픽스처·빌더, 비동기·예외를 어떻게 검증하는지 기록한다.
   **저장소 관례가 이 문서의 취향 규칙보다 우선한다** (신뢰성 규칙만 예외).
   테스트가 아예 없으면 그 언어의 가장 흔한 러너를 쓰고, 그 선택을 말한다
2. **단위와 계약을 정한다.** 공개 인터페이스(내보낸 함수, 클래스 메서드, 컴포넌트 props/events)를 찾고,
   입력 차원과 관찰 가능한 결과(반환값·상태 변화·계약에 속하는 외부 호출·던지는 예외)를 나열한다
3. **행위 표를 만든다.** 정상 경로 → 경계 → 에러 경로 → 상태 전이. 도출 방법은 `references/edge-cases.md`.
   **테스트를 쓰기 전에** 표를 적어둔다 (플랜의 슬라이스, 테스트 파일 상단 주석, PR 본문 중 하나)
4. **테스트를 쓴다.** 아래 구조·이름·더블·단정 규칙을 따른다
5. **돌린다.** 쓴 테스트를 전부 실행하고 통과를 눈으로 본다.
   버그 수정이면 수정 *전에* 돌려서 **버그 때문에** 실패하는 것까지 확인한다
6. **스멜 체크리스트로 자가 점검한다** (`references/checklist.md`). 걸리는 게 있으면 고치고 넘긴다
7. **보고한다.** 커버리지 퍼센트가 아니라 **어떤 행위를 덮었는지**로. 못 덮은 행위와 이유를 함께

## 유닛 테스트가 하는 일

한 번에 네 가지다 — 행위를 실행 가능한 형태로 **명세**하고, 약속이 깨질 때만 깨지는 **회귀 방어**를 하고,
테스트가 어려우면 설계가 잘못됐다는 **설계 피드백**을 주고, 이름만 읽어도 무슨 일을 하는지 알게 **문서**가 된다.
아래 규칙은 전부 이 네 가지를 위한 것이다.

## 구현이 아니라 행위를 테스트한다

- **MUST** 공개 인터페이스를 통해 테스트한다. private은 간접적으로 덮인다.
  private에 테스트가 따로 필요해 보이면 그건 별도 단위로 **추출하라는 신호**다
- **MUST** 관찰 가능한 결과에 단정한다 — 반환값, 상태 변화, 계약에 속하는 외부 호출.
  내부 호출 순서·중간 변수·private 헬퍼 호출 횟수가 아니다
- 행위를 보존하는 리팩터링은 테스트를 깨뜨리면 **안 된다**. private 메서드 이름을 바꿨는데 테스트가 깨지면
  그 테스트가 구현을 박아둔 것이다 — 다시 쓴다

```
// BAD — 구현을 박아둔다
test("getUser는 cache.get 다음 db.find를 호출한다", () => {
  service.getUser(42)
  expect(cache.get).toHaveBeenCalledBefore(db.find)
})

// GOOD — 약속을 말한다
test("캐시에 없는 사용자 id면 저장소에서 읽어 반환한다", async () => {
  store.seed(aUser({ id: 42, name: "Ada" }))
  const user = await service.getUser(42)
  expect(user).toEqual(aUser({ id: 42, name: "Ada" }))
})
```

## 구조 — 테스트 하나에 행위 하나

Arrange–Act–Assert(= Given–When–Then)를 눈에 보이게 쓴다. 주석 세 개를 실제로 남긴다.

```
test("<조건> → <행동>하면 <기대 결과>", () => {
  // given  — 이 행위에 필요한 최소한의 세계만 만든다
  // when   — 테스트 대상 행동 하나
  // then   — 하나의 결과에 대한 단정
})
```

- **MUST** 테스트 하나 = 행위 하나. 같은 결과의 여러 면(응답의 status + body)을 함께 단정하는 건 괜찮다
- **SHOULD** Act는 하나. 예외: 행위 자체가 순서일 때 — 상태 전이(`open → close → reopen`), 멱등성, 이중 제출.
  시작 상태를 만들기 위한 호출은 Act가 아니라 Arrange다
- Arrange를 정직하게 유지한다. 단정 1줄에 준비 30줄이면 단위가 의존을 너무 많이 가졌거나 레벨이 틀렸다

### 이름

- **MUST** 조건 + 행동 + 기대 결과의 문장으로 쓴다. **실패한 테스트의 이름만 보고 어떤 약속이 깨졌는지 알아야 한다**
  - `"만료된 토큰 → refresh가 새 토큰을 반환한다"`
  - `"빈 목록 → 플레이스홀더를 렌더한다"`
  - `"일일 한도 초과 금액 → LimitExceededError로 거절한다"`
- **언어는 저장소 관례를 따른다.** 기존 테스트가 한글 문장 이름이면 한글, 영문이면 영문.
  한 저장소 안에서 섞는 게 어느 쪽을 고르는 것보다 나쁘다
- **MUST NOT** 메서드 이름을 그대로 옮기거나 번호를 붙인다 (`test_getUser_2`, `should work`, `정상_케이스`)

**금지 테스트명 — 이 이름이 보이면 무엇을 단정하는지 모른다는 뜻이다.**

```
should work        정상_케이스        renders
works correctly    성공 / 실패        handles errors
test1 / test2      기본 동작          edge case
it works           잘 되는지 확인      동작 확인
```

공통 증상: **조건과 기대 결과 중 하나 이상이 빠졌다.** `handles errors`는 어떤 에러를
어떻게 다루는지 말하지 않는다 → `"결제 게이트웨이 타임아웃 → 주문을 pending으로 두고 재시도 큐에 넣는다"`.

## 무엇을 테스트할지

줄(line)이 아니라 행위 표를 덮는다.

- **정상 경로** — 약속의 기본형
- **경계** — 비어있음/0/1/다수, 최소/최대, 한도 정확히 그 값과 하나 넘은 값
- **에러 경로** — 잘못된 입력, 협력자 실패, 타임아웃. 잘못됐을 때 어떻게 구는지도 계약이고,
  대부분의 코드에서 가장 덜 테스트된 부분이다
- **상태 전이** — 모드가 있으면 각 모드가 아니라 **의미 있는 전이**를 테스트한다

지나칠 것: 단순 위임(pass-through), 생성된 코드, 프레임워크 자체, 서드파티 라이브러리.

커버리지 퍼센트는 결과지 목표가 아니다. **단정이 허술한 100%는 날카로운 70%보다 나쁘다** — 없는 확신을 만들어낸다.
조직이 커버리지 게이트를 걸어두었으면 **행위를 덮어서** 채운다. 단정 없는 테스트로 숫자를 올리지 않는다.

엣지 케이스를 브레인스토밍이 아니라 체계적으로 도출하는 방법: `references/edge-cases.md`.

## 레벨을 고른다

- **단위**는 독립적으로 테스트 가능한 가장 작은 행위 — 보통 함수·클래스·모듈 — 이고,
  협력자는 **내가 소유한 경계**(외부 시스템·라이브러리를 감싼 우리 인터페이스)에서만 가짜로 바꾼다
- 대부분이 **접착 코드**(배선·설정·I/O 오케스트레이션)인 코드는 유닛 테스트로 만들면 목 덩어리가 되고 잘 깨진다.
  접착부는 경계에서 얇은 통합 테스트로 덮고, 유닛 테스트는 그 안의 로직에 쓴다
- 값진 로직이 테스트하기 어려운 껍데기(UI 핸들러, I/O 루프, 프레임워크 콜백) 안에 갇혀 있으면
  **로직을 순수 단위로 추출해서** 테스트한다. 테스트하기 어려운 코드는 모킹 과제가 아니라 설계 신호다
- 아래로 민다: 로직 계층의 빠른 유닛 테스트 다수 + 경계의 통합 테스트 소수 >
  느린 바깥 계층으로 모든 분기를 다시 훑기

## 결정성과 격리

가끔 실패하는 테스트는 팀에게 **실패를 무시하는 습관**을 가르친다. flaky는 잡음이 아니라 결함이다.

- **MUST NOT** 실제 시간·난수·네트워크에 의존한다. 클럭을 주입하고, 난수는 시드를 고정하거나 주입하고, I/O 경계는 가짜로
- **MUST NOT** 테스트가 소유하지 않은 실제 파일시스템을 건드린다 (격리된 임시 디렉터리나 인메모리 fs만)
- **MUST NOT** 실행 순서나 공유 가변 상태에 의존한다. 각 테스트가 자기 세계를 만들고 치운다. 병렬 실행이 안전해야 한다
- **MUST NOT** sleep으로 기다린다. 기간이 아니라 **실제 신호**(프로미스·콜백·조건)를 기다린다
- 같은 입력 → 같은 결과. 어느 머신에서든, 몇 시든, 어떤 로케일·타임존에서든 (그게 테스트 대상 행위가 아닌 한)
- **SHOULD** 밀리초 단위로 끝난다. 느린 스위트는 변경 전마다 돌리지 않게 되고, 안 돌리는 스위트는 아무것도 지키지 않는다.
  무거운 준비가 필요하면 그 테스트는 통합 레벨에 속한다

## 비동기와 시간

- 결과의 신호를 기다린 뒤 단정한다. 진행 중에 단정하지 않는다
- 시간 기반 로직(디바운스·재시도/백오프·만료·타임아웃)은 **MUST** 가짜 클럭이나 주입된 스케줄러를 쓰고 명시적으로 진행시킨다
- 비동기 경로의 실패는 **MUST** 테스트를 실패시킨다. `await` 하나를 빠뜨리거나 rejection을 삼키는 fire-and-forget은
  **엉뚱한 이유로 통과하는 테스트**를 만든다 — 통과하는데 아무것도 지키지 않는 상태가 가장 위험하다
- 동시성 주장(스레드 안전성·재진입·취소)은 연산을 명시적으로 교차시킨 자기 테스트가 필요하다.
  플랫폼이 주는 수단(제어 가능한 스케줄러, 래치, 수동 태스크 스테핑)을 쓴다. sleep과 기대는 수단이 아니다

## 의존성 종류가 더블 전략을 결정한다

더블을 쓸지 말지를 취향으로 정하지 않는다. **대상이 무엇에 의존하는지가 답을 정한다.**

| 의존성 종류 | 예 | 전략 |
|---|---|---|
| **in-process** | 순수 계산, 메모리 상태, I/O 없음 | 더블 없음. 진짜로 호출한다 |
| **local-substitutable** | 로컬 대역이 있는 것 (PGLite, 인메모리 FS, testcontainers) | 대역을 띄워 진짜에 가깝게. 목 쓰지 않는다 |
| **remote-owned** | 우리가 소유한 원격 (사내 API, 다른 서비스) | 우리 인터페이스로 감싸고 인메모리 어댑터로 테스트 |
| **true-external** | 통제 못 하는 서드파티 (Stripe, 카카오, Twilio) | 우리 인터페이스로 감싸고 그것을 모킹. **서드파티 SDK를 직접 모킹하지 않는다** |

위에서 아래로 갈수록 더블이 필요해진다. **분류를 건너뛰고 바로 목을 잡는 것이 과잉 모킹의 시작이다.**

## 테스트 더블 (mock · stub · fake)

더블은 경계에서 격리하는 도구지 기본값이 아니다.

- **SHOULD** 빠르고 결정적이고 만들기 쉬우면 진짜 객체를 쓴다 (순수 로직, 값 객체, 인메모리 구현)
- **읽는 것은 stub, 시키는 것은 verify.** 단위가 *읽는* 것은 정해진 값을 돌려주게 하고,
  단위가 *하는* 일(협력자에게 보내는 명령)은 그 호출이 계약일 때만 단정한다 — 예: "결제 요청을 정확히 한 번 보낸다"
- **MUST NOT** 내가 소유하지 않은 것을 모킹한다. 서드파티 API는 우리 경계 인터페이스로 감싸고 그걸 모킹한다.
  라이브러리 내부를 모킹하면 테스트가 남의 구현에 용접된다
- **과잉 모킹 스멜**: 같은 테스트 안에서 내가 설정한 인자로 목이 호출됐는지만 확인하고 있으면,
  그건 단위가 아니라 **내가 방금 테스트에 쓴 배선**을 테스트하는 것이다. 지우거나 다시 쓴다

```
// BAD — 목 메아리: 테스트가 자기 설정을 검증한다
test("메일을 보낸다", async () => {
  mailer.send.mockResolvedValue({ ok: true })
  await notifier.notify(user)
  expect(mailer.send).toHaveBeenCalledWith(expect.anything())
})

// GOOD — 나가는 명령이 계약이므로 그 내용을 단정한다
test("이메일이 인증된 사용자 → 그 주소로 환영 메일을 정확히 한 통 보낸다", async () => {
  const mailer = new FakeMailer()
  await new Notifier(mailer).notify(aUser({ email: "ada@example.com", verified: true }))
  expect(mailer.sent).toEqual([{ to: "ada@example.com", template: "welcome" }])
})
```

## 단정

- **SHOULD** 행위를 표현하는 **가장 구체적인 사실**에 단정한다. "null이 아니다"보다 정확한 값,
  필드 하나씩 찍기보다 구조 동등성, "뭔가 던진다"보다 예외 타입·코드
- **MUST NOT** 우연한 세부에 단정한다 — 순서가 없는 컬렉션의 순서, 바뀔 문구, 공백.
  무해한 변경마다 빌드를 빨갛게 만든다
- 통짜 스냅샷은 최후 수단이다. 모든 변경에 실패하니 아무도 이유를 읽지 않게 된다.
  스냅샷을 쓰면 작게, 계약에 해당하는 부분만
- 실패 출력이 원인을 가리켜야 한다. expected vs actual이 찍히는 형태를 쓰고,
  값만으로 설명이 안 될 때만 메시지를 붙인다

## DRY보다 가독성

테스트는 **가장 나쁜 순간에, 쓰지 않은 사람이** 읽는다.

- DRY보다 **DAMP**(서술적이고 의미 있는 문장). 테스트마다 이야기가 완결되면 약간의 중복은 괜찮다
- 시끄러운 객체 생성은 **빌더/팩토리**로 뺀다 (`aUser(overrides)`).
  Arrange 전체를 공용 setup에 숨기지 않는다 — 숨겨진 준비는 **보이지 않는 이유로** 테스트를 통과·실패시킨다
- **MUST NOT** 테스트 본문에 분기(`if`·`switch`·조건부 `try/catch`)를 넣는다. 분기가 있는 테스트는 자기 테스트가 필요하다.
  데이터만 만드는 루프와 플랫폼 관용 예외 단정(`assertThrows`, `pytest.raises`, `expect().rejects`)은 괜찮다.
  **파라미터화/테이블 테스트가 허용된 반복 형태다** — 경계값 표에 쓴다
- 테스트 데이터가 *왜* 그 값인지 말하게 한다. 의도로 이름 짓고(`EXPIRED_TOKEN`, `MAX_LENGTH_NAME`),
  행위가 의존하는 필드만 넣고 나머지는 빌더 기본값에 맡긴다. 매직 값은 어느 부분이 결과를 만드는지 독자가 추측하게 만든다

## 버그 수정은 재현이 먼저

**MUST** 수정 전에 실패하는 테스트를 쓰고, 실패를 한 번 눈으로 본다 (red → green).
그 테스트는 **버그 때문에** 실패해야 한다. 준비 실수로 실패한 것은 회귀를 지킨다는 증거가 못 된다.

## 구조가 바뀌면 테스트는 대체한다 — 쌓지 않는다

리팩터링으로 여러 얕은 모듈이 하나의 인터페이스 뒤로 들어갔다면,
**옛 모듈들에 붙어 있던 테스트는 폐기물이다. 지운다.**

남겨두면 세 가지가 생긴다.

- 사라진 구조에 결합된 테스트가 **다음 리팩터링을 막는다**
- 통과해도 아무것도 보장하지 않는다 — 그 인터페이스로는 이제 아무도 호출하지 않는다
- 테스트 수가 늘어 커버리지가 좋아 보인다. **가짜 확신이 없는 것보다 나쁘다**

새 테스트는 **새 인터페이스에서** 쓴다. 관측 가능한 결과를 단정하고 내부 상태를 보지 않는다.

> **구현을 바꿨을 때 테스트도 바꿔야 한다면, 그 테스트는 인터페이스 너머를 보고 있다.**

리팩터링 전후로 **전체 테스트 결과가 같아야 한다.** 하나라도 다르면 그건 리팩터링이 아니라
동작 변경이다. 절차는 `refactor`.

## 기존 코드의 버그를 발견하면

기존 코드에 테스트를 쓰다 보면 현재 동작이 명세·문서·명백한 의도와 다른 걸 발견한다.

- **MUST NOT** 버그 동작을 계약인 양 테스트로 박제한다
- **MUST NOT** 테스트를 통과시키려고 운영 코드를 슬쩍 고친다 — 그건 자기 리뷰가 필요한 별개의 변경이다
- **SHOULD** *의도한* 동작으로 테스트를 쓰고, skip/expected-failure로 표시하고 불일치를 가리키는 주석을 남긴 뒤
  **사용자에게 명시적으로 보고한다**
- 의도가 불분명하면(버그일 수도, 문서화 안 된 결정일 수도) 티켓·명세 주인에게 묻는다. 추측하지 않는다

## 의도적으로 행위가 바뀔 때

명세가 바뀌어서 실패하는 테스트는 회귀가 아니다. 테스트를 고치는 것이 그 변경의 일부다.

- 같은 변경 안에서, **새 약속**을 말하도록 기대값을 의도적으로 갱신한다.
  새 코드가 뱉는 값을 그대로 받아적는 게 아니다
- **MUST NOT** 초록이 될 때까지 단정을 느슨하게 만든다. 아무것도 지키지 않는 테스트가 남는다
- 회귀인지 명세 변경인지 판단이 안 되면 동전 던지기가 아니라 **티켓 주인에게 묻는다.** 멈춘다

UserService 테스트 6건 추가 — ./gradlew test --tests "*UserServiceTest*" → 6 passed

  경계: 대소문자만 다른 이메일 / 앞뒤 공백 / 최대 길이 254자

## 하지 말 것

| 안티패턴 | 실제 비용 |
|---|---|
| 이 문서를 따르려고 새 테스트 프레임워크 도입 | 스위트가 두 벌이 되고 CI·관례가 갈라진다 |
| 내부 호출 순서·private 호출 횟수 단정 | 리팩터링마다 빨간 빌드. 행위는 하나도 안 지킴 |
| 정상 경로만 테스트 | 실제 장애의 대부분이 에러 경로에서 온다 |
| 단정 없는 테스트로 커버리지 채우기 | 없는 확신을 만들어낸다. 숫자만 초록 |
| 목이 호출됐는지만 확인 | 내가 방금 쓴 테스트 배선을 테스트한다 |
| sleep으로 비동기 기다리기 | 느리고 flaky. CI 부하에 따라 결과가 바뀐다 |
| 실제 시간·난수·네트워크 사용 | 특정 시각·로케일·회선 상태에서만 깨진다 |
| 테스트를 쓰고 안 돌려보기 | 통과한다고 적은 것이 실제로는 실패 |
| 버그 수정 테스트의 실패를 확인 안 함 | 회귀를 지키는지 증거가 없다 |
| 기존 버그를 테스트로 박제 | 버그가 계약이 되고, 고치려는 사람이 테스트에 막힌다 |
