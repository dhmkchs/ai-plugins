# Jira Create

**나쁜 티켓은 나쁜 플랜을 만들고 나쁜 PR로 끝난다.** 이 스킬의 목적은 티켓을 빨리 만드는 게 아니라
`plan`이 바로 계획으로 옮길 수 있는 티켓을 만드는 것이다.

## 0. 전제 확인

Atlassian MCP 도구가 없으면 여기서 멈추고 사용자에게 알린다. 추측으로 진행하지 않는다.

```
atlassianUserInfo                    연결 확인
getAccessibleAtlassianResources      cloudId 획득 (대부분의 도구가 요구)
```

**도구 이름과 필수 인자는 실제 도구 목록에서 확인한다.** 이 문서의 이름은 Atlassian Rovo MCP 기준이며,
다른 Jira MCP를 쓰면 이름이 다르다. 없는 도구를 호출하지 말고 있는 것으로 대체한다.

## 1. 중복부터 찾는다

티켓을 만들기 전에 같은 게 이미 있는지 본다. 중복 티켓은 나중에 병합하는 비용이 만드는 비용보다 크다.

```
searchJiraIssuesUsingJql
  jql: project = PROJ AND text ~ "중복 이메일" AND statusCategory != Done ORDER BY updated DESC
```

비슷한 게 있으면 **새로 만들지 말고 사용자에게 보여준다.** "이미 PROJ-118이 있는데 여기 붙일까요, 새로 만들까요?"

## 2. 내용을 채운다 — 네 가지가 없으면 티켓이 아니다

| 요소 | 없으면 생기는 일 |
|---|---|
| **문제** — 지금 무엇이 잘못됐나 (현상, 재현 조건) | 무엇을 고쳤는지 확인할 수 없다 |
| **영향** — 누가, 얼마나 자주, 얼마나 심각하게 | 우선순위를 정할 수 없다 |
| **완료 조건** — 무엇이 되면 끝인가 (검증 가능하게) | 끝났는지 아무도 모른다 |
| **범위 밖** — 이 티켓에서 안 하는 것 | 스코프가 무한정 늘어난다 |

대화에서 채울 수 없는 항목은 **묻는다.** 특히 완료 조건은 절대 지어내지 않는다.

**제목 규칙**: 문제나 결과를 쓰고 해결책을 쓰지 않는다. 해결책을 제목에 박으면 더 나은 방법을 검토할 여지가 사라진다.

- 나쁨: "UserService에 existsByEmail 추가"
- 좋음: "중복 이메일로 계정이 두 개 생성됨"

**본문 문법에 제약이 있다.** Jira는 마크다운이 아니라 ADF로 저장하고, 코드 블록·중첩 목록은
조용히 뭉개진다. `references/jira-markdown.md`의 안전한 문법만 쓴다.
완료 조건은 반드시 `- [ ]` 체크박스로 쓴다 — 그래야 Jira에서 클릭 가능하고 나중에 자동 체크된다.

**설명 템플릿**
```
## 문제
<현상 — 관찰된 사실만. 추정은 "추정"으로 표시>

## 재현
1. ...
2. ...
기대: ...  실제: ...

## 영향
<누가 / 빈도 / 심각도. 숫자가 있으면 숫자로>

## 완료 조건
- [ ] <검증 가능한 조건>
- [ ] <검증 가능한 조건>

## 범위 밖
- <명시적으로 제외>

## 참고
<로그, 스크린샷, 관련 티켓, 코드 위치>
```

버그면 재현 절차가 필수다. 재현을 모르면 그것 자체를 티켓에 쓴다 — "재현 조건 미확인"이 빈칸보다 낫다.

## 3. 프로젝트·이슈타입·필드를 조회한다

**프로젝트 키와 이슈 타입을 추측하지 않는다.** 틀리면 생성이 실패하거나 엉뚱한 곳에 만들어진다.

```
getVisibleJiraProjects                프로젝트 목록 → 사용자에게 확인
getJiraProjectIssueTypesMetadata      해당 프로젝트의 이슈 타입 (Bug/Task/Story는 팀마다 다르다)
getJiraIssueTypeMetaWithFields        필수 필드와 허용값 (커스텀 필드가 있는 팀이 많다)
```

`.work/config.json`에 기본값이 있으면 그것을 쓰되, 첫 사용이면 조회 결과로 확인받고 저장한다.

```json
{ "jira": { "projectKey": "PROJ", "defaultIssueType": "Task" } }
```

담당자를 지정하려면 `lookupJiraAccountId`로 accountId를 얻는다. 이름 문자열로는 지정되지 않는다.

## 4. 미리보기 → 승인 → 생성

**생성 전에 반드시 전문을 보여주고 승인받는다.** Jira 생성은 되돌리기 번거롭고, 팀에 알림이 나간다.

```
아래 내용으로 만들까요?
  프로젝트: PROJ / 타입: Bug / 담당: 미지정 / 라벨: backend
  제목: 중복 이메일로 계정이 두 개 생성됨
  ---
  <설명 전문>
```

승인 후 `createJiraIssue`.

**실패하면 응답의 어느 필드가 문제인지 먼저 읽는다.** Jira는 거부된 필드를 이름으로 알려준다.
팀마다 커스텀 필드 설정이 달라서, 없는 필드나 허용되지 않은 값 때문에 실패하는 경우가 대부분이다.

- 필수가 아닌 필드가 거부됐으면 **그 필드를 빼고 한 번 더 시도**한다. 뺀 필드는 사용자에게 보고한다
- 필수 필드가 비어서 실패했으면 `getJiraIssueTypeMetaWithFields`로 허용값을 조회해 채운다
- **최대 3회.** 그 이상은 설정 문제이므로 멈추고 오류 원문을 보여준다

같은 요청을 그대로 반복하지 않는다. 매번 무엇을 바꿨는지 말한다.

## 5. 마무리

생성된 키와 URL을 출력하고 다음 단계를 제시한다.

```
PROJ-123 생성됨 — https://<site>.atlassian.net/browse/PROJ-123
다음: /work:plan PROJ-123 으로 작업 플랜을 만들 수 있습니다.
```

관련 티켓이 있으면 링크를 제안한다 (`getIssueLinkTypes`로 사용 가능한 링크 타입 확인).

## 하지 말 것

| 안티패턴 | 실제 비용 |
|---|---|
| 완료 조건을 지어내기 | 잘못된 기준으로 개발이 끝난다 |
| 프로젝트 키·이슈타입 추측 | 생성 실패, 또는 엉뚱한 보드에 등록 |
| 중복 확인 생략 | 같은 일을 두 사람이 한다 |
| 제목에 해결책 박기 | 더 나은 접근을 검토할 여지가 사라진다 |
| 승인 없이 생성 | 팀 알림이 나가고 되돌리기 번거롭다 |
| 한 티켓에 여러 문제 | 플랜도 PR도 쪼갤 수 없어진다 |

**문제가 두 개면 티켓도 두 개다.** 묶고 싶으면 에픽이나 이슈 링크를 쓴다.
