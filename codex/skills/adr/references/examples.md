# ADR 예시 — 좋은 것 vs 나쁜 것

## 나쁜 ADR — 사후 정당화

```markdown
# ADR-3: React Query 사용
- 상태: Accepted
## 결정
서버 상태 관리에 React Query를 쓴다. 업계 표준이고 좋다.
```

문제: 대안 없음, 맥락 없음, 결과 없음. "좋다"는 근거가 아니다. 이건 ADR이 아니라 메모다.
6개월 뒤 SWR로 바꿀지 고민할 때 이 문서는 아무 도움이 안 된다.

## 좋은 ADR — 판단을 재현 가능하게

```markdown
# ADR-3: 서버 상태에 TanStack Query 채택
- 상태: Accepted · 날짜: 2026-02-10 · 결정자: FE팀

## 컨텍스트
화면 12개가 같은 리소스를 각자 fetch·캐시해 중복 요청과 stale UI가 반복된다.
전역 스토어(Zustand)에 서버 데이터까지 넣으면서 캐시 무효화 로직이 컴포넌트마다 흩어졌다.
제약: 팀 4명, 이미 Zustand로 클라이언트 상태를 관리 중, 6주 내 안정화 필요.

## 고려한 대안
### A — Zustand에 서버 상태도 계속 둔다
- 장점: 새 의존성 없음, 학습 비용 0
- 단점: 캐시 무효화·재요청·중복제거를 직접 구현, 이게 지금 버그의 원인
### B — TanStack Query
- 장점: 캐시·무효화·중복제거·재시도가 내장, 서버/클라 상태 분리가 강제됨
- 단점: 새 의존성·개념(queryKey, staleTime) 학습, Zustand와 역할 경계 교육 필요
### C — SWR
- 장점: 더 가벼움, API 단순
- 단점: 뮤테이션·낙관적 업데이트 지원이 B보다 약함, 우리 폼 화면에 부족

## 결정
**B 채택.** 우리 버그의 근본 원인은 "서버 상태를 클라이언트 상태 도구로 관리"한 것이다.
B는 그 분리를 도구 차원에서 강제한다. C도 후보였으나 뮤테이션 비중이 커 B의 기능이 값지다.
→ 일반 원칙이 아니라, "뮤테이션·낙관적 업데이트가 많은 우리 화면 구성"이 B를 골랐다.

## 결과
- 긍정: 캐시 무효화 로직이 컴포넌트에서 사라짐, 중복 요청 제거
- 비용: 팀이 queryKey 설계 규약을 익혀야 함 (별도 컨벤션 문서 필요)
- 후속: Zustand는 순수 클라이언트 상태(모달·폼 로컬)만 담당하도록 경계 문서화 → 후속 티켓
```

## 자주 쓰는 결정 카탈로그 (ADR 후보)

- 모듈 경계: 모놀리스 vs 모듈형 모놀리스 vs 서비스 분리
- 상태 관리: 서버 상태 도구 선택, 전역 vs 지역 경계
- 인증: 세션 쿠키 vs JWT, 토큰 저장 위치
- 데이터 모델: 정규화 정도, soft delete vs hard delete, 다형성 표현
- API 스타일: REST vs GraphQL vs RPC (→ `api` 스킬과 연계)
- 폴더 구조: 레이어별 vs 기능별(FSD 등)
- 비동기: 동기 호출 vs 큐/이벤트

각 항목이 §언제 쓰나의 "둘 이상 대안 + 되돌리기 비쌈"을 만족하면 ADR로 남긴다.
