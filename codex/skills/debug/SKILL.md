# Bug Hunt

**원인을 모르는 상태에서는 코드를 고치지 않는다.** 이 한 줄이 이 스킬의 전부다.
증상을 보고 바로 패치하면 (1) 증상만 가려서 같은 버그가 다른 형태로 돌아오고 (2) 왜 고쳤는지 설명할 수 없어 리뷰가 통과되지 않는다.

## 5단계

### 1. REPRODUCE — 재현을 고정한다

재현되지 않는 버그는 고칠 수 없고, 고쳤는지도 알 수 없다.

- 가장 작은 실패 입력을 만든다
- 그 입력을 **실패하는 테스트**로 먼저 박아둔다 (수정 전에)
- 실행 방법을 한 줄 명령으로 만든다

```bash
npm test -- -t "재현 케이스"
./gradlew test --tests "*.FooTest.reproCase"
```

화면에서 발생하는 버그면 `browser`로 재현을 고정한다 — 콘솔 에러와 실패한 요청이 원인을 바로 지목하는 경우가 많다.

재현이 안 되면: 입력·환경·타이밍·순서 중 무엇이 다른지 목록으로 적고 하나씩 맞춰본다.
**테스트가 단독 실행은 통과하고 전체 실행은 실패**하면 테스트 간 상태 공유 문제다 (전역 변수, DB, 정적 필드, 시간).

### 2. LOCALIZE — 범위를 반씩 줄인다

추측으로 파일을 뒤지지 않는다. 이분 탐색한다.

**입력 이분 탐색**: 실패 입력을 반으로 줄여도 실패하는가. 최소 실패 입력까지 줄인다.

**경로 이분 탐색**: 데이터 흐름의 중간 지점에서 값을 확인한다. 그 지점에서 값이 이미 틀렸으면 앞쪽, 맞으면 뒤쪽.

```javascript
console.log('[chk1]', JSON.stringify({ input, intermediate }));
```
```java
System.err.println("[chk1] " + input + " -> " + intermediate);
```

**히스토리 이분 탐색**: 예전에 동작했다면 `git bisect`가 가장 빠르다.
```bash
git bisect start HEAD <good-commit>
git bisect run npm test -- -t "재현 케이스"
```

**경계 우선 확인**: 대부분의 버그는 계층 경계에 있다 — 파싱, 직렬화, 타입 변환, 외부 호출, DB 매핑.
내부 알고리즘보다 경계를 먼저 의심한다.

### 3. HYPOTHESIZE — 가설을 쓰고 실험을 고른다

한 번에 한 가설. 가설은 반증 가능해야 한다.

```
가설: 중복 원소에서 카운터가 두 번 증가한다.
예측: 입력 [1,1]에서 count가 2가 아니라 3이 된다.
실험: 루프 안에 count 로그 1줄 추가.
```

예측이 틀리면 가설을 버린다. **맞을 때까지 가설을 수정하지 말고, 틀린 가설은 기록하고 버린다.**
같은 가설을 두 번 시도하고 있으면 멈추고 1단계로 돌아간다.

`references/failure-catalog.md`에 증상별 원인 후보표가 있다. 증상이 익숙하면 여기서 먼저 찾는다.

### 4. FIX — 최소 수정

- **한 번에 한 가지만 고친다.** 두 곳을 동시에 고치면 무엇이 효과가 있었는지 모른다
- 근본 원인을 고친다. 증상 억제(`try/catch`로 삼키기, 값 하드코딩, 조건 추가로 특정 입력 회피)는 금지
- 원인을 정말 못 찾아 우회했다면 **우회임을 코드 주석과 PR에 명시**한다. 숨기면 다음 사람이 같은 함정에 빠진다
- 수정 범위가 커지면 멈추고 재설계를 제안한다

수정 후 확인 순서:
1. 재현 테스트가 통과하는가
2. 기존 테스트 전체가 통과하는가 (기준선과 비교)
3. 인접 엣지케이스도 통과하는가

### 5. GUARD — 회귀 방지

- 1단계에서 만든 실패 테스트를 **남긴다** (지우지 않는다)
- 같은 부류의 케이스를 2~3개 추가한다
- 같은 실수가 다른 곳에도 있는지 검색한다 — 이게 점수 차이를 만든다

```bash
# 같은 패턴을 다른 곳에서도 쓰고 있는지
grep -rn "동일한 잘못된 패턴" src
```

같은 실수가 반복되는 패턴이라면 린트 규칙이나 타입으로 막을 수 있는지도 검토한다. 사람의 주의력에 의존하는 방어는 다시 뚫린다.

## 보고 형식

수정이 끝나면 아래 형식으로 정리한다. 그대로 PR 설명이나 이슈 코멘트가 된다.

```
## 버그 리포트
- 증상: <관찰된 것>
- 재현: <명령 또는 최소 입력>
- 근본 원인: <파일:라인> — <왜 틀렸는가>
- 왜 지금까지 안 잡혔나: <테스트 공백 / 특정 조건에서만 발생>
- 수정: <무엇을 어떻게>
- 검증: 재현 테스트 통과 / 기존 N개 전부 통과 / 추가 케이스 M개
- 같은 패턴 다른 위치: <있음(목록) / 없음(확인함)>
- 남은 리스크: <있으면 명시, 없으면 "없음">
```

"왜 지금까지 안 잡혔나"를 답하는 것이 원인을 정말 이해했다는 증거다.

## 금지 사항

| 금지 | 이유 |
|---|---|
| 원인 모르고 패치 | 다른 버그 유발, 설명 불가 |
| 여러 곳 동시 수정 | 효과 귀속 불가 |
| `try/catch`로 예외 삼키기 | 버그를 숨김, 나중에 더 크게 터짐 |
| 재현 테스트 삭제 | 회귀 방지 장치 제거 |
| 로그·디버그 코드 방치 | 프로덕션 로그가 오염되고 리뷰에서 되돌아온다 (`console.log`, `System.out.println`, 주석 처리된 코드) |
| 실패 테스트를 skip/주석 처리 | 최악. 발견되면 신뢰 상실 |

## AI에게 디버깅을 맡길 때

`pair`의 디버깅 프롬프트 템플릿을 쓴다. 핵심은:
- 증상 + 정상 케이스 + 이미 배제한 것을 함께 준다
- **"수정 코드는 아직 주지 마라, 검증할 실험을 제안해라"**를 먼저 요구한다
- 받은 원인 설명을 로그로 직접 확인한 뒤에 패치를 요청한다
