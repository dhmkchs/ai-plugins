# 자주 나오는 설계 결정과 근거 문장

PR 설명이나 리뷰 코멘트에서 "왜 그렇게 했어?"에 답할 때 쓰는 재료.
**정답은 없다. 근거가 있으면 논의가 되고, 없으면 취향 싸움이 된다.**

## 검증을 어디서 하는가

| 선택 | 근거 문장 |
|---|---|
| 경계(DTO/컨트롤러) | "형식 검증은 진입점에서 끝내 도메인이 유효한 값만 다루게 했습니다. 형식 오류(400)와 규칙 위반(409)의 응답이 달라야 해서 분리했습니다." |
| 도메인 객체 생성자 | "불변식을 타입으로 보장하려고 생성자에서 검증했습니다. 유효하지 않은 객체가 존재할 수 없습니다." |
| 서비스 | "여러 엔티티를 봐야 하는 규칙이라 한 객체로는 판단할 수 없어 서비스에 두었습니다." |

## 에러를 예외로 던지나 값으로 반환하나

| 선택 | 근거 문장 |
|---|---|
| 예외 | "예상 못한 상황이고 호출부가 대응할 수 없어 예외로 올렸습니다. 프레임워크의 에러 핸들러가 응답 매핑을 담당합니다." |
| Result 타입 | "실패가 정상 흐름의 일부라 타입으로 드러냈습니다. 호출부가 처리를 잊을 수 없습니다." |

일관성이 선택보다 중요하다. **기존 코드베이스가 하나를 쓰고 있으면 그것을 따른다.**

## 트랜잭션 경계

- "서비스 메서드를 트랜잭션 경계로 잡았습니다. 컨트롤러에 두면 응답 직렬화까지 트랜잭션에 들어가고, 리포지토리에 두면 여러 저장이 원자적이지 않습니다."
- "외부 호출(메일 발송)은 커밋 후로 옮겼습니다. 트랜잭션 안에서 외부 호출을 하면 롤백 시 취소할 수 없고 커넥션을 오래 점유합니다."

## 동시성 / 중복 처리

- "애플리케이션 레벨 존재 검사만으로는 경쟁 조건에서 중복이 생깁니다. DB 유니크 제약을 최종 방어선으로 두고, 제약 위반 예외를 409로 변환했습니다."
- "낙관적 락(`@Version`)을 선택했습니다. 충돌이 드물고 락 대기 비용을 피하고 싶었습니다. 충돌이 잦다면 비관적 락이 맞습니다."

## 페이지네이션

- "offset 방식으로 구현했습니다. 요구사항의 데이터 규모에서 충분하고 구현이 단순합니다. 수십만 건 이상이면 커서 기반으로 바꿔야 합니다." — 한계를 함께 말하는 것이 핵심

## 캐시를 넣을까

기본은 **넣지 않는다.** 근거:
- "측정된 성능 문제가 없어 캐시를 넣지 않았습니다. 무효화 전략이라는 복잡도를 근거 없이 도입하지 않으려 했습니다."

넣는다면 무효화 전략을 반드시 함께 정한다. 무효화 없는 캐시는 버그를 캐싱한다.

## 추상화(인터페이스)를 언제 만드나

만드는 근거:
- "외부 시스템 경계라 테스트에서 대체가 필요해 인터페이스를 두었습니다."
- "구현이 실제로 2개 이상 존재합니다."

만들지 않는 근거:
- "구현이 하나뿐이고 교체 계획이 없어 인터페이스를 만들지 않았습니다. 필요해지면 추출하는 편이 쉽습니다."

**구현체가 하나인 인터페이스는 과설계 신호로 읽힌다.** 외부 경계가 아니면 만들지 않는다.

## 동기 vs 비동기

- "즉시 일관성이 필요한 부분은 동기로, 실패해도 재시도 가능한 부분(알림, 집계)은 비동기로 분리했습니다."
- "메시지 큐를 도입하지 않았습니다. 요구사항 규모에서 운영 복잡도가 이득을 넘습니다."

## DTO를 따로 만드나

- "엔티티를 API 응답으로 직접 노출하지 않았습니다. 내부 스키마 변경이 API 계약을 깨지 않게 하고, 민감 필드가 실수로 새어 나가는 걸 막습니다."

이건 거의 항상 DTO 분리가 정답이다. 엔티티 직접 노출은 내부 스키마를 API 계약으로 굳혀버린다.

## 라이브러리를 쓸까 직접 구현할까

- "표준 라이브러리로 충분해 의존성을 추가하지 않았습니다."
- "직접 구현하면 엣지케이스(타임존, 윤년)를 놓칠 위험이 커서 검증된 라이브러리를 썼습니다."

의존성 추가 전에 팀 정책을 확인한다. 라이선스·보안 스캔·번들 크기·업그레이드 부채가 따라오고, 되돌리기 어렵다.

## 로그를 어디에 얼마나

- "요청 진입·이탈과 도메인 규칙 위반만 로깅했습니다. 루프 안 로깅은 성능과 가독성을 모두 해칩니다."
- "개인정보(이메일, 전화번호)는 마스킹했습니다."

개인정보가 로그에 평문으로 남는 것은 실제 사고로 이어진다. 로깅 코드를 쓸 때마다 확인한다.

## 성능을 어디까지 신경쓰나

원칙: **측정 없이 최적화하지 않는다.**
- "요구사항의 응답 시간 기준을 로컬에서 측정해 확인했습니다(평균 40ms). 추가 최적화는 근거가 없어 하지 않았습니다."
- "N+1 쿼리는 실제로 발생하는 것을 로그로 확인하고 fetch join으로 해결했습니다."

측정값을 제시하는 것과 추정을 말하는 것의 차이가 크다. 숫자를 하나라도 넣는다.

## 일정이 부족했을 때

- "남은 시간을 새 기능보다 기존 기능의 엣지케이스에 썼습니다. 동작 범위가 확실한 편이 낫다고 판단했습니다."

이 판단은 거의 항상 옳다. 무엇을 미뤘는지 후속 티켓으로 남기면 잊히지 않는다.
