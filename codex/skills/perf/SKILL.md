# Web Performance

성능 작업의 실패는 대부분 같은 자리에서 난다 — **재기 전에 고친다.**
감으로 고치면 무엇이 효과가 있었는지 모르고, 다음에 느려졌을 때 처음부터 다시 시작한다.

순서를 지킨다: **기준선 → 원인 확정 → 수정 → 재측정 → 예산 고정.**
재측정이 없으면 이 스킬을 돌린 의미가 없다. 3단계까지만 하고 "개선했습니다"라고 하지 않는다.

`browser`(동작하나)·`ui`(시안대로인가)·`e2e`(다음에도 지켜지나)와 축이 다르다.
이 스킬은 **얼마나 빠른가**를 본다.

## 지표 수치는 출처가 이긴다

아래 임계값은 **2026-08 기준**이다. 구글이 지표와 임계값을 바꿔온 이력이 있다
(FID → INP 교체, CLS 세션 윈도 도입). **숫자를 인용하기 전에 출처를 확인한다.**

| 출처 | 확인할 것 |
|---|---|
| `https://web.dev/articles/vitals` | 현재 Core Web Vitals 구성과 임계값 |
| `https://developer.chrome.com/docs/lighthouse/performance/performance-scoring` | Lighthouse 점수 가중치 |
| `https://web.dev/articles/cls` | CLS 세션 윈도 정의 |

문서와 이 표가 다르면 **문서가 맞다.** 이 표를 근거로 사용자에게 단정하지 않는다.

## 0. 무엇으로 잴 것인가 — 먼저 정한다

우선순위대로 하나를 고른다. 위에서 되면 아래는 보지 않는다.

1. **Playwright + CDP** (기본) — 이 저장소에 이미 있다. 스로틀·캐시·반복을 직접 통제할 수 있어
   재현성이 가장 좋다. 아래 절차는 이걸 전제로 한다
2. **chrome-devtools MCP** — 트레이스 인사이트(LCP 분해·CLS 범인)를 바로 준다. 있으면 3단계에서 쓴다
3. **Lighthouse CLI** (`npx lighthouse <url> --output=json`) — 점수 형식 보고가 필요할 때만

Playwright가 없으면 여기서 멈추고 설치를 요청한다.

```bash
npm i -D @playwright/test && npx playwright install chromium
```

chrome-devtools MCP를 쓰려면 사용자에게 이 설정을 요청한다. **없다고 중단하지 않는다** — 1번으로 간다.

```json
"chrome-devtools": {
  "type": "local",
  "command": ["npx", "-y", "chrome-devtools-mcp@latest"]
}
```

## 진행 체크리스트

작업 시작 시 이 블록을 복사해 상태로 삼는다. 페이즈를 조용히 건너뛰지 않기 위한 것이다.

```
Perf:
- [ ] 1. 기준선 측정 (3회 중앙값, 조건 기록)
- [ ] 2. 지표 판정 (어느 지표가 나쁜가 — 나쁜 게 없으면 여기서 끝낸다)
- [ ] 3. 원인 확정 (추측 아님 — 근거 명시)
- [ ] 4. 수정 (영향 큰 것부터 하나씩)
- [ ] 5. 재측정 (개선분을 숫자로)
- [ ] 6. 예산 고정 (회귀 방지)
```

## 1단계: 기준선 — 고치기 전에 잰다

**측정 조건을 고정하지 않은 숫자는 비교할 수 없다.** 개발 머신은 빠르고 캐시는 더워서,
조건을 안 맞추면 수정 후 숫자가 좋아져도 그게 수정 덕인지 캐시 덕인지 모른다.

고정할 것: 캐시 비움 · 네트워크·CPU 스로틀 · 뷰포트 · **3회 중앙값**.

`scripts/perf.mjs`를 프로젝트에 복사해 실행한다. 준비된 그대로 동작한다.

```bash
node perf.mjs http://localhost:3000/ 3 > perf-before.json
```

스크립트가 고정하는 것 — **기준선과 재측정에 같은 파일·같은 인자를 쓴다.**

- 모바일 뷰포트 412×915 (DPR 2)
- 느린 4G(RTT 150ms · 1.6Mbps) + **CPU 4배 스로틀** — Lighthouse 기본 프로파일
- 매 회차 캐시 비움
- 지정 횟수 반복 후 **지표별 중앙값**

뽑는 값: TTFB · FCP · LCP(+**어느 요소인지**) · CLS(+**어느 노드가 움직였는지**) · TBT ·
리소스 종류별 KB. 조건 문자열도 함께 출력하므로 보고에 그대로 붙인다.

관측자(`PerformanceObserver`)는 `goto` 이전에 심는다 — 나중에 심으면 초기 엔트리를 놓친다.
측정 창 확보를 위한 4초 고정 대기가 들어 있는데, **`browser` 스킬이 금지하는 고정 대기와 다르다.**
거기서 금지하는 것은 상호작용 대기이고, 여기 것은 의도된 관측 구간이다.

**프로덕션 URL에 대고 반복 측정하지 않는다.** 로컬 프로덕션 빌드(`npm run build && npm run preview`)에서 잰다.
개발 서버에서 잰 숫자는 소스맵·HMR·미압축 번들 때문에 실제와 무관하다.

## 2단계: 판정 — 나쁜 게 없으면 여기서 끝낸다

**2026-08 기준.** 위 「출처가 이긴다」를 먼저 읽는다.

| 지표 | 좋음 | 개선 필요 | 나쁨 | 무엇인가 |
|---|---|---|---|---|
| TTFB | < 800ms | < 1.8s | ≥ 1.8s | 서버·네트워크가 첫 바이트를 주기까지 |
| FCP | < 1.8s | < 3s | ≥ 3s | 뭐라도 처음 그려지기까지 |
| **LCP** | < 2.5s | < 4s | ≥ 4s | 가장 큰 콘텐츠가 그려지기까지 |
| **CLS** | < 0.1 | < 0.25 | ≥ 0.25 | 레이아웃이 얼마나 튀는가 |
| TBT | < 200ms | < 600ms | ≥ 600ms | 메인 스레드가 막힌 총 시간 |

굵은 것이 Core Web Vitals다. **INP는 랩에서 못 잰다** — 실제 사용자 상호작용이 있어야 나온다.
랩에서는 **TBT를 INP의 대리 지표**로 본다. INP 실값이 필요하면 필드 데이터(CrUX·RUM)를 봐야 하고,
이 스킬로는 답할 수 없다. 그렇게 말한다.

**CLS 주의**: 위 스크립트의 CLS는 전체 시프트 합이고, CWV 정의(최대 세션 윈도)보다 **크게 나온다.**
회귀 감시와 범인 찾기에는 충분하지만, **절대값으로 "CLS 나쁨"이라 단정하지 않는다.**

전부 「좋음」이면 **여기서 멈추고 그렇게 보고한다.** 억지로 개선안을 만들지 않는다.
이미 빠른 페이지에 최적화를 얹으면 복잡도만 늘고 다음 사람이 못 읽는다.

## 3단계: 원인 확정 — 추측을 보고하지 않는다

나쁜 지표마다 **무엇을 보면 확정인가**가 정해져 있다. 근거 없이 조치를 권하지 않는다.

### LCP — 네 구간 중 어디가 먹었는지 가른다

```
LCP = TTFB + 리소스 발견 지연 + 리소스 로드 시간 + 렌더 지연
```

| 구간이 지배적 | 확정 근거 | 조치 방향 |
|---|---|---|
| TTFB | `ttfb`가 LCP의 40% 이상 | 서버·캐시·CDN. 프론트에서 못 고친다 |
| 발견 지연 | LCP 리소스의 `startTime`이 늦다 (CSS·JS가 발견을 막음) | `<link rel=preload>`, CSS import 체인 제거 |
| 로드 시간 | LCP 리소스 `transferSize`가 크다 | 포맷(WebP/AVIF)·크기·압축 |
| 렌더 지연 | 리소스는 일찍 왔는데 LCP가 늦다 | 렌더 블로킹 CSS/JS, 폰트 대기 |

LCP 요소가 무엇인지는 스크립트의 `lcpElement`가 알려준다. **어느 요소인지 모른 채 추측하지 않는다.**

### CLS — 범인을 노드로 지목한다

`worstShifts`의 `nodes`가 실제로 움직인 요소다. 흔한 원인 순서대로:

1. `width`/`height` 없는 이미지 → 반드시 명시(또는 `aspect-ratio`)
2. 폰트 스왑 → `font-display: optional` 또는 폰트 preload
3. 위에서 삽입되는 배너·광고·알림 → 자리를 미리 확보
4. 늦게 오는 데이터로 높이가 바뀌는 목록 → 스켈레톤을 실제 높이로

**노드를 지목하지 못하면 조치를 권하지 않는다.** "이미지에 크기를 넣으세요"는 범인이 이미지일 때만 맞다.

### TBT / 번들 — 미사용을 주장하려면 측정한다

"이 라이브러리는 안 쓰는 것 같다"는 추측이다. **커버리지로 확정한다.**

```javascript
await page.coverage.startJSCoverage();
await page.goto(url, { waitUntil: 'load' });
const cov = await page.coverage.stopJSCoverage();

for (const e of cov) {
  const total = e.source?.length ?? 0;
  if (total < 20_000) continue;
  // V8 커버리지 범위는 중첩된다. 바깥에서 안쪽 순으로 덮어써야 한다.
  // 단순히 count>0 범위를 합산하면 중복 계산돼 "미사용"이 음수로 나온다
  const hit = new Uint8Array(total);
  e.functions.flatMap(f => f.ranges)
    .sort((a, b) => a.startOffset - b.startOffset || b.endOffset - a.endOffset)
    .forEach(r => hit.fill(r.count > 0 ? 1 : 0, r.startOffset, Math.min(r.endOffset, total)));
  const used = hit.reduce((s, v) => s + v, 0);
  console.log(`${Math.round(100 - used / total * 100)}% 미사용  ${Math.round(total/1024)}KB  ${e.url}`);
}
```

첫 로드 기준 미사용 비율이다. **미사용 = 삭제 가능이 아니다** — 다른 경로에서 쓰일 수 있다.
"첫 화면에서 안 쓰이므로 **지연 로드** 후보"까지가 이 측정이 지지하는 주장이다.
삭제를 권하려면 코드베이스에서 참조가 0인 것을 따로 확인한다.

## 4단계: 수정 — 영향 순서대로, 하나씩

**추정 개선폭이 없는 것은 손대지 않는다.** "일반적으로 좋은" 최적화를 나열하지 않는다.

한 번에 하나씩 고친다. 여러 개를 한꺼번에 바꾸면 어느 것이 효과였는지 알 수 없고,
그 지식이 없으면 다음 회귀 때 또 처음부터 한다.

자주 나오는 조치와 그 전제:

| 조치 | 언제만 유효한가 |
|---|---|
| 이미지 포맷·크기 축소 | LCP 요소가 이미지이고 로드 시간이 지배적일 때 |
| `preload` 추가 | 리소스가 **늦게 발견**될 때. 이미 일찍 오는 것에 붙이면 다른 리소스를 밀어낸다 |
| 코드 스플리팅 | 커버리지상 첫 화면 미사용 비율이 클 때 |
| `defer`/`async` | 스크립트가 렌더 블로킹으로 확인됐을 때 |
| 폰트 `display` 조정 | CLS 범인이 텍스트 노드일 때 |
| `preconnect` | 그 origin으로 실제 요청이 가고, 늦게 갈 때. **요청 0건이면 제거 대상이다** |

## 5단계: 재측정 — 이 단계를 생략하면 작업이 끝난 게 아니다

**같은 스크립트, 같은 조건으로** 다시 잰다.

```bash
node perf.mjs http://localhost:3000/ 3 > perf-after.json
```

| 지표 | before | after | 변화 |
|---|---|---|---|
| LCP | 3,840ms | 2,180ms | **−1,660ms** |
| CLS | 0.24 | 0.02 | **−0.22** |
| scriptKB | 812 | 340 | **−472KB** |

**개선분이 측정 노이즈 안이면 개선이 아니다.** 3회 중앙값 기준 ±10% 안의 변화는
"개선했다"고 보고하지 않는다. 그럴 땐 회차를 5회로 늘려 다시 잰다.

숫자가 나빠졌으면 되돌린다. 좋아 보이는 최적화가 실제로는 손해인 경우가 흔하다
(과한 preload, 지나친 스플리팅으로 요청 수 폭증).

## 6단계: 예산으로 고정한다 — 회귀 방지

고치고 끝내면 다음 기능이 다시 무너뜨린다. 프로젝트에 예산을 둔다.

```json
// .work/perf-budget.json
{ "url": "/", "lcp": 2500, "cls": 0.1, "tbt": 200, "scriptKB": 400 }
```

예산 파일을 3번째 인자로 넘기면 중앙값과 비교해 **초과 시 exit 1**로 끝난다. CI에 그대로 건다.

```bash
node perf.mjs http://localhost:4173/ 3 .work/perf-budget.json
# 예산 초과: lcp 2840 > 2500   → exit 1
```

**예산은 현재값보다 조금 여유 있게 잡는다.** 현재값 그대로 잡으면 노이즈로 CI가 빨개지고, 곧 무시된다.

번들 크기가 바뀌는 변경(의존성 추가, 큰 컴포넌트 신설)은 `review`에서 이 스킬 재실행을 요구한다.

## 보고 형식

```
## 성능 (모바일 · 느린 4G · CPU 4x · 3회 중앙값 · 로컬 프로덕션 빌드)
- LCP 3,840ms (나쁨) → 2,180ms (좋음)   LCP 요소: IMG /hero.png
- CLS 0.24 → 0.02                      범인: IMG(크기 미지정), 상단 알림 배너
- TBT 610ms → 180ms                    scriptKB 812 → 340
- TTFB 210ms (좋음, 변화 없음 — 서버는 문제 아님)

확정 근거
- LCP: hero.png 1.2MB, 로드 시간이 LCP의 62%. WebP 변환 + width/height 명시
- 번들: chart 라이브러리 첫 화면 미사용 94% (커버리지) → 동적 import로 분리

INP: 랩에서 측정 불가. TBT로 대리 판정함. 실값은 필드 데이터 필요
예산: .work/perf-budget.json 생성 (lcp 2500 / cls 0.1 / tbt 200 / scriptKB 400)
```

**"체감상 빨라졌습니다"로 끝내지 않는다.** 조건과 숫자를 같이 쓴다.
측정 조건을 안 적으면 다음 사람이 비교할 수 없어서 그 숫자는 없는 것과 같다.

## 하지 말 것

| 안티패턴 | 실제 비용 |
|---|---|
| 재기 전에 고치기 | 무엇이 효과였는지 영원히 모른다 |
| 개발 서버에서 측정 | 소스맵·HMR·미압축 — 실제와 무관한 숫자 |
| 1회 측정으로 판정 | 회차 간 편차가 개선폭보다 크다 |
| 스로틀 없이 측정 | 개발 머신에서는 전부 「좋음」이 나온다 |
| 여러 최적화를 한꺼번에 | 효과 귀속 불가, 손해 본 것도 못 찾는다 |
| 커버리지 없이 "안 쓰는 것 같다" | 다른 경로에서 쓰던 코드를 지운다 |
| 미사용 = 삭제로 직행 | 지연 로드까지가 측정이 지지하는 결론이다 |
| 랩에서 INP 값을 보고 | 상호작용 없이는 나오지 않는 지표다 |
| 이미 빠른 페이지 최적화 | 복잡도만 남고 다음 사람이 못 읽는다 |
| 재측정 없이 "개선했습니다" | 검증이 아니라 주장이다 |
| 프로덕션에 반복 측정 | 실사용자 트래픽·지표를 오염시킨다 |

## work 사슬 연결

- 화면 스킬 네 축: `browser`=동작하나 · `ui`=시안대로인가 · `perf`=얼마나 빠른가 · `e2e`=다음에도 지켜지나.
- 번들·이미지·폰트·초기 렌더를 건드린 변경이면 `review`가 이 스킬을 요구한다.
- 예산 파일(`.work/perf-budget.json`)을 만들었으면 `pr` 본문에 before/after 표를 넣는다.
- 원인이 서버·CDN이면 프론트에서 못 고친다. `ticket`으로 넘기고 여기서 끝낸다.
- 되돌리기 비싼 판단(SSR 전환, 번들러 교체)까지 갔으면 `adr`로 근거를 남긴다.
