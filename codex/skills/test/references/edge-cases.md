# 엣지 케이스 도출

브레인스토밍하지 않는다. **입력 차원마다** 아래 순서를 돈다.
순서를 지키면 빠뜨린 게 드러나고, 같은 부류를 열 개씩 쓰는 낭비가 사라진다.

```
동등 분할 → 경계 → 트랩 값 → 거부 → 조합·반복 → 관련성으로 가지치기
```

## 1. 동등 분할

각 입력을 **단위가 똑같이 다뤄야 하는 값들의 집합**으로 나눈다.
한 분할당 테스트 하나면 충분하다. 같은 분할에서 값 열 개를 뽑는 건 실행 시간만 늘리고 확신은 안 늘린다.

```
할인율 계산 amount
  분할 A: amount < 0          → 거부
  분할 B: 0 ≤ amount < 10000  → 할인 0
  분할 C: 10000 ≤ amount      → 5%
```

세 분할 → 테스트 세 개. `5000`과 `7000`을 둘 다 넣는 건 같은 분할의 중복이다.

## 2. 경계

분할 사이의 **울타리**에서 버그가 산다. 한도 정확히 그 값, 하나 안, 하나 밖.

```
9999 → 0원      (경계 하나 안)
10000 → 500원   (경계 정확히 — off-by-one이 여기서 잡힌다)
10001 → 500원   (경계 하나 밖)
```

경계 세트는 **파라미터화/테이블 테스트**로 묶는다. 표 자체가 "경계를 체계적으로 봤다"는 증거가 된다.

## 3. 트랩 값

타입별로 "유효한데도 실제 코드를 깨뜨리는" 값들이다.

| 입력 타입 | 볼 것 |
|---|---|
| 문자열 | 빈 문자열, 공백만, 앞뒤 공백, 아주 긴 값, 유니코드(이모지·결합 문자·RTL), 하위 시스템에서 의미를 갖는 문자(따옴표·개행·`<`·`%`·경로 구분자) |
| 숫자 | 0, 음수, 도메인 최소/최대, 부동소수 정밀도(`0.1+0.2`), 표현 가능하면 NaN/Infinity, 정수 오버플로 경계 |
| 컬렉션 | 빈 컬렉션, 원소 1개, 중복 원소, 이미 정렬됨·역정렬, O(n²)나 페이지네이션이 드러날 만큼 큰 것 |
| nullable/optional | 플랫폼이 구분한다면 null·undefined·**필드 없음**은 서로 다른 세 경우. "빈 값인 필드"와 "없는 필드"도 다르다 |
| 날짜·시간 | 월·연 경계, 윤일, DST 전환, UTC가 아닌 타임존, epoch·극단값 — **단위가 날짜 연산을 할 때만** |
| ID·키 조회 | 없는 키, 대소문자만 다른 키, 중복 키, 삭제됐는데 참조가 남은 키 |

한글·이모지는 한국어 서비스에서 실제로 자주 터진다. 길이 제한을 **문자 수**로 재는지 **바이트 수**로 재는지가
DB 컬럼 제약과 어긋나면 저장 시점에 깨진다 — 문자열 길이 제한이 있는 단위는 이 케이스를 넣는다.

## 4. 거부

명세가 말하는 **모든 검증 규칙**은 "그 입력이 거부된다"는 테스트를 하나씩 갖는다.
그리고 *어떻게* 거부되는지까지 단정한다 — 예외 타입·에러 코드. "죽지는 않는다"는 단정이 아니다.

```
// BAD
expect(() => svc.register("not-an-email")).toThrow()

// GOOD
expect(() => svc.register("not-an-email"))
  .toThrow(new InvalidEmailError("not-an-email"))
```

계약의 **네거티브 스페이스도 계약**이다. 거부 규칙 하나가 테스트되지 않으면 그 규칙은 조용히 사라질 수 있다.

## 5. 조합과 반복

- 각각은 유효한 두 극단을 **함께** (최대 길이 이름 + 빈 목록)
- **같은 연산 두 번** — 멱등성, 이중 제출, 재시도. 단위가 다시 들어올 수 있는 구조면 반드시

```
"이미 취소된 주문을 다시 취소하면 상태가 그대로 CANCELLED다"   // 멱등
"같은 요청 id로 두 번 결제하면 결제는 한 번만 일어난다"          // 이중 제출
```

## 6. 관련성으로 가지치기

**단위의 계약이 반응할 여지가 있는 값만 넣는다.**
날짜 연산을 하는 단위에는 DST가 필요하지만, 문자열 포매터에는 필요 없다.
관련 없는 엣지는 스위트를 부풀리기만 하고 신뢰를 더하지 않는다.

가지치기 기준: **이 케이스가 깨졌을 때, 그게 버그인가?** 아니면 넣지 않는다.

## 도출 결과를 적는 형태

테스트를 쓰기 전에 이 표를 남긴다. 플랜의 슬라이스 아래, 테스트 파일 상단 주석, PR 본문 중 한 곳.

```
UserService.register(email, name)
| 차원   | 케이스                     | 기대                        |
|--------|----------------------------|-----------------------------|
| email  | 신규 정상                  | 저장 + 환영 메일 1통        |
| email  | 대소문자만 다른 기존 값    | DuplicateEmailException     |
| email  | 앞뒤 공백                  | 정규화 후 저장              |
| email  | 형식 오류                  | InvalidEmailError           |
| email  | 254자 / 255자              | 통과 / 거부 (경계)          |
| name   | 빈 문자열                  | ValidationError             |
| 반복   | 같은 이메일 연속 두 번     | 두 번째는 거부, 저장 1건    |
| 협력자 | 메일 발송 실패             | 가입은 유지, 예외 전파 안 함 |
```

표를 만드는 과정에서 못 본 케이스가 항상 한둘 나온다. **그게 이 단계의 값이다.**
