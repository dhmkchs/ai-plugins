# Jira 본문 작성 제약 (ADF)

Jira Cloud는 본문을 마크다운이 아니라 **ADF(Atlassian Document Format)** 라는 JSON 트리로 저장한다.
MCP나 API가 마크다운을 받아주더라도 변환 과정에서 **지원하지 않는 문법은 조용히 뭉개진다** —
에러가 나지 않고 그냥 평문이 되거나 사라진다. 그래서 티켓 본문에 쓸 문법을 미리 제한해야 한다.

## 안전한 문법

| 문법 | 표기 |
|---|---|
| 제목 | `## 제목` (1~6단계) |
| 문단 | 빈 줄로 구분 |
| 굵게 / 기울임 / 인라인코드 | `**굵게**` `_기울임_` `` `code` `` |
| 링크 | `[텍스트](https://...)` |
| 순서 없는 목록 | `- 항목` (**한 단계만**) |
| 순서 있는 목록 | `1. 항목` (**한 단계만**) |
| 체크박스 | `- [ ] 항목` / `- [x] 항목` |
| 표 | `\| A \| B \|` + 구분행 |
| 구분선 | `---` |

## 피할 문법 — 대체 방법

| 쓰지 말 것 | 왜 | 대신 |
|---|---|---|
| 코드 블록 (```) | 평문으로 붕괴, 줄바꿈 소실 | 인라인 코드 + 링크. 긴 코드는 저장소 경로로 |
| 중첩 목록 | 들여쓰기가 사라져 평평해짐 | 한 단계로 펴거나 표로 |
| 인용문 (`>`) | 지원 불안정 | 일반 문단 |
| 이미지 삽입 | 첨부 업로드가 별도 API | 링크로 |
| HTML 태그 | 이스케이프되어 그대로 노출 | 마크다운 문법으로 |
| 각주·정의목록 | 미지원 | 표로 |

**표 셀 안에 `|`를 쓰지 않는다.** 파이프로 열을 나누기 때문에 셀 안의 `|`는 열을 어긋나게 만든다.
필요하면 `｜`(전각) 같은 다른 문자로 바꾸거나 표를 쓰지 않는다.

## 체크박스 = 완료 조건

`- [ ]` 는 ADF의 `taskItem`으로 저장되고, **Jira 화면에서 실제로 클릭 가능한 체크박스**가 된다.
그래서 완료 조건은 반드시 체크박스로 쓴다.

```markdown
### Acceptance Criteria
- [ ] 이미 존재하는 이메일로 가입 시 409와 코드 DUPLICATE_EMAIL 반환
- [ ] 대소문자가 달라도 같은 이메일로 취급
```

`pr` 단계에서 충족된 항목을 자동으로 체크할 수 있는 것도 이 형식일 때만이다.
평문 목록(`- 항목`)으로 쓰면 체크가 불가능하다.

**체크 상태를 갱신할 때는 순서(인덱스)로 지목하게 되므로**, 체크 직전에 목록을 다시 읽어
지금 상태를 확인한 뒤 갱신한다. 조회와 갱신 사이에 누가 본문을 편집하면 엉뚱한 항목이 체크된다.

## 본문 갱신 시 주의

Jira 본문 갱신은 대개 **전체 교체(PUT)** 다. 그래서 두 가지가 문제가 된다.

**덮어쓰기** — 조회한 뒤 갱신하는 사이에 다른 사람이 편집하면 그 편집이 사라진다.
갱신 직전에 다시 읽어 최신 본문 위에서 수정한다.

**무한 누적** — 진행 상황을 본문 뒤에 계속 덧붙이면 같은 내용이 쌓인다.
덧붙이기 전에 **같은 제목의 섹션이 이미 있는지 확인하고, 있으면 교체한다.**

```markdown
---
## 작업 기록 (2026-08-03)
...
```

이 형태로 표식을 넣어두면 다음 갱신 때 같은 표식을 찾아 교체할 수 있다.
진행 상황은 본문보다 **코멘트**에 남기는 편이 안전하다 — 코멘트는 추가만 되고 서로 덮어쓰지 않는다.

## 길이

본문이 길면 Jira 화면에서 접히고 검색도 잘 안 걸린다.
**상세 설계는 저장소의 플랜 파일(`.agents/plans/<TICKET>.md`)에 두고 티켓에는 경로만 적는다.**

티켓 본문에 들어갈 것: 배경, 내용, 링크 문서 or 자료, Acceptance Criteria (표준 4섹션).
플랜 파일에 둘 것: 정찰 노트, 슬라이스, 코드 경로, 설계 판단.

이렇게 나누면 티켓은 "무엇을 왜"에 집중하고, 코드 세부는 코드 옆에 남는다.
플랜 파일에는 ADF 제약이 없으므로 코드 블록도 중첩 목록도 자유롭게 쓸 수 있다.
